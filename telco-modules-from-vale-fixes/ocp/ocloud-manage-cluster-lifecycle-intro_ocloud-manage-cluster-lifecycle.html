Template-based cluster provisioning and management at scale

Managing bare metal Red Hat OpenShift Container Platform clusters at scale introduces challenges that grow with fleet size. As the number of sites increases, maintaining consistency across cluster configurations, coordinating hardware allocation, and executing lifecycle operations such as upgrades and scaling become increasingly complex and error-prone when handled manually or through bespoke automation.

The O-Cloud Manager addresses these challenges by providing template-based infrastructure and cluster lifecycle management through a GitOps-based workflow, with REST APIs for programmatic access.

The O-Cloud Manager implements the O-RAN Alliance O2 IMS specification through its REST APIs, which are designed for integration with Service Management and Orchestration (SMO) systems used in telecommunications environments. However, SMO integration is optional. The same REST APIs provide programmatic access to any external system. You can also manage the underlying custom resources directly, or through a GitOps workflow, without using the REST APIs. This enables the O-Cloud Manager to support any multi-cluster, bare metal deployment that benefits from template-based cluster provisioning and lifecycle management.

The O-Cloud Manager separates reusable cluster blueprints from site-specific deployment parameters:

  • Platform engineers define immutable ClusterTemplate resources that specify the cluster topology, hardware requirements, and configuration policies for a class of clusters.

  • Site engineers create ProvisioningRequest resources that reference a template and supply only the site-specific values such as network addresses and cluster names.

This separation means that platform-wide changes, such as a new firmware baseline or an updated network policy, can be rolled out by versioning a template rather than editing each cluster individually. The O-Cloud Manager validates each request against the template schema, allocates hardware from managed resource pools, and orchestrates the end-to-end lifecycle flow by using the SiteConfig Operator, Red Hat OpenShift GitOps, and the Topology Aware Lifecycle Manager.

All lifecycle operations, provisioning, configuration, scaling, and upgrades, are driven through the ProvisioningRequest custom resource, providing a single point of control for each managed cluster. The REST APIs provide programmatic access to the same operations to enable automation and integration with external management systems, such as SMO frameworks.

O-Cloud Manager key components

The O-Cloud Manager uses several custom resources (CRs) to manage the cluster lifecycle. You use these resources when configuring templates, provisioning clusters, and managing hardware.

ClusterTemplate CR

An immutable blueprint that defines the cluster topology, hardware defaults, and configuration policies for a class of clusters. Each ClusterTemplate CR references ConfigMap resources that supply cluster installation defaults and policy template defaults. These defaults are merged with site-specific values at provisioning time.

ProvisioningRequest CR

A mutable resource that represents the desired state of a single managed cluster. One ProvisioningRequest CR represents one cluster. Creating a ProvisioningRequest CR triggers provisioning. Updating it enables Day 2 operations such as configuration changes, scaling, and upgrades. Each ProvisioningRequest CR references a ClusterTemplate CR and supplies site-specific parameters or optional configuration overrides.

HardwareProfile CR

An optional resource that defines target firmware levels and BIOS settings for a class of servers. When specified in a ClusterTemplate CR, the O-Cloud Manager applies the hardware profile during initial provisioning or as a Day 2 update.

BareMetalHost CR

Represents a physical server registered in the hub cluster inventory. The Bare Metal Operator manages this resource, but the O-Cloud Manager uses the BareMetalHost CR for hardware selection. Each BareMetalHost CR includes metadata labels used for resource selection and defines a BMC connection for power management and hardware inspection.

ResourcePool CR

Groups bare metal resources at a site for allocation. When processing a ProvisioningRequest, the O-Cloud Manager selects hosts from the appropriate resource pool based on the resource selectors defined in the ClusterTemplate.

Location and OCloudSite CRs

Represent the infrastructure hierarchy. A Location CR identifies a geographic place where infrastructure is deployed. An OCloudSite CR represents a logical site that references a parent Location CR. One or more ResourcePool resources reference the OCloudSite CR to group bare-metal servers at that site.

O-Cloud Manager REST APIs

The O-Cloud Manager exposes REST APIs that provide endpoints for external systems to manage infrastructure and orchestrate the full cluster lifecycle through standard HTTP operations.

The REST API endpoints meet the O-RAN Alliance O2 IMS specification, which enables management by a Service Management and Orchestration (SMO) framework in telecommunications environments. However, SMO integration is optional. The same REST APIs provide programmatic access to any external system.

The REST APIs are served over a single route on the hub cluster.

Inventory API

O2ims_infrastructureInventory/v2 — Query the physical infrastructure including resource pools, individual resources, locations, sites, resource types, and deployment managers.

Artifacts API

O2ims_infrastructureArtifacts/v1 — List available cluster templates, query template parameter schemas, and retrieve preconfigured defaults.

Provisioning API

O2ims_infrastructureProvisioning/v1 — Create, update, and delete provisioning requests to drive cluster lifecycle operations including provisioning, scaling, configuration changes, and upgrades.

Cluster API

O2ims_infrastructureCluster/v1 — Query provisioned node clusters, cluster resources, and node cluster types. Manage cluster event subscriptions for notifications on cluster state changes.

Monitoring API

O2ims_infrastructureMonitoring/v1 — Query and acknowledge alarms raised by managed clusters. Manage alarm subscriptions for event-driven monitoring and alerting.

Declarative hardware management for bare-metal servers

In large-scale deployments with heterogeneous hardware across multiple sites, manually tracking which servers meet the requirements for each cluster and ensuring consistent firmware baselines becomes challenging. The O-Cloud Manager automates hardware allocation and firmware configuration as part of the provisioning workflow, by using the infrastructure hierarchy of Location, OCloudSite, and ResourcePool resources to organize servers across your fleet.

Servers are registered in the hub cluster as BareMetalHost CRs with metadata labels that identify resource pool membership, server type, and other characteristics. The Bare Metal Operator connects to each host’s BMC and inspects the physical hardware. The O-Cloud Manager uses this inspection data to populate its own hardware allocation resources with CPU, memory, NIC, and storage details. This enables automatic hardware-aware selection without requiring manual intervention to verify server specifications at each site.

The HardwareProfile CR defines the firmware configuration for a class of servers. This eliminates manual BMC configuration across your fleet and ensures that every server of a given class runs a consistent, baseline configuration before cluster installation. The hardware manager applies the profile during initial provisioning or as a Day 2 update when firmware patching or performance tuning is required. A HardwareProfile is optional. You can provision servers without a profile if you manage firmware and BIOS settings manually.

When processing a ProvisioningRequest CR, the O-Cloud Manager selects servers from resource pools using a two-stage filtering process defined in the ClusterTemplate CR. This ensures the correct class of server is assigned to the correct node role without manual server-by-server assignment, even in racks with mixed hardware:

Label-based filtering

Selects BareMetalHost CRs by labels such as server type, location identifiers, or resource selector labels.

Hardware data filtering

Further filters hosts based on hardware inspection data, matching criteria such as CPU architecture, thread count, memory size, NIC speed and count, and storage type and capacity.

Together, these filtering stages and the optional HardwareProfile application automate the path from bare metal inventory to installation-ready hardware without manual intervention at each site.

O-Cloud Manager cluster lifecycle workflow

The O-Cloud Manager manages bare-metal clusters from initial environment preparation through ongoing operations. All post-provisioning operations are configured through updates to the ProvisioningRequest custom resource (CR).

Prepare

Install the O-Cloud Manager on the hub cluster, configure the GitOps repository, and define ClusterTemplate CR resources with cluster installation defaults, configuration policies, and hardware management settings. Optionally, define HardwareProfile resources for firmware and BIOS management.

Onboard

Register bare-metal servers in resource pools by creating BareMetalHost resources with resource selector labels that identify server type, location, and hardware characteristics. The Bare Metal Operator connects to each host’s BMC, inspects the physical hardware, and populates a HardwareData CR used for resource selection during provisioning.

Provision

Create a ProvisioningRequest that references a validated ClusterTemplate and supplies site-specific parameters. The O-Cloud Manager allocates matching hardware from the resource pool, applies any specified firmware and BIOS settings, renders a ClusterInstance resource, and orchestrates the cluster installation through the SiteConfig Operator. For single-node Red Hat OpenShift Container Platform clusters, image-based installation (IBI) is supported as an alternative provisioning method. After installation, configuration policies are applied and monitored for compliance.

Operate

Update the ProvisioningRequest to drive Day 2 operations on the running cluster, including configuration changes, firmware and BIOS updates, worker node scaling, and cluster upgrades.

Configure the GitOps repository for O-Cloud Manager resources

Configure a Git repository with the directory layout required by the O-Cloud Manager, including cluster templates, configuration policy definitions, hardware profiles, and server inventory. ArgoCD synchronizes this repository content to the hub cluster where the O-Cloud Manager uses it for cluster provisioning.

This repository layout differs from the GitOps Zero Touch Provisioning (ZTP) GitOps layout. In GitOps ZTP, the Git repository contains a ClusterInstance CR for each site, representing the full cluster definition. In the O-Cloud Manager flow, the repository contains reusable templates, defaults, and policies. Individual clusters are instantiated by creating a ProvisioningRequest CR that references a template and supplies site-specific parameters. The ProvisioningRequest CR can be applied directly to the hub cluster or managed through a separate GitOps repository.
Prerequisites

  • The O-Cloud Manager Operator is installed on the hub cluster.

  • The Red Hat OpenShift GitOps Operator is installed.

  • You have a Git repository accessible by ArgoCD on the hub cluster.

Procedure

  1. Create your Git repository. See the following recommended directory layout:

    ├── clustertemplates/
│   ├── hardwareprofiles/
│   ├── inventory/
│   └── version_4.Y.Z/
│       ├── sno-ran-du/
│       │   ├── clusterinstance-defaults-v1.yaml
│       │   ├── policytemplates-defaults-v1.yaml
│       │   ├── pull-secret.yaml
│       │   ├── extra-manifest/
│       │   ├── ns.yaml
│       │   └── sno-ran-du-v4-Y-Z-1.yaml
│       └── std-ran-du/
│           ├── clusterinstance-defaults-v1.yaml
│           ├── policytemplates-defaults-v1.yaml
│           ├── pull-secret.yaml
│           ├── ns.yaml
│           └── std-ran-du-v4-Y-Z-1.yaml
└── policytemplates/
    └── version_4.Y.Z/
        ├── sno-ran-du/
        │   ├── ns.yaml
        │   ├── msc-binding.yaml
        │   └── sno-ran-du-pg-v4-Y-Z-v1.yaml
        ├── std-ran-du/
        │   ├── ns.yaml
        │   ├── msc-binding.yaml
        │   └── std-ran-du-pg-v4-Y-Z-v1.yaml
        └── source-crs/

    • clustertemplates/ contains CRs that define how clusters are provisioned:

      • hardwareprofiles/ contains HardwareProfile custom CRs that define firmware levels and BIOS settings for classes of bare-metal servers.

      • inventory/ contains BareMetalHost CRs for sites where server inventory is managed through GitOps.

      • version_4.Y.Z/ organizes content by the target Red Hat OpenShift Container Platform release version.

      • sno-ran-du/ and std-ran-du/ are template directories for single-node and standard multi-node cluster topologies respectively.

      • sno-ran-du-v4-Y-Z-1.yaml is a ClusterTemplate CR that defines the cluster blueprint, including the parameter schema, node group definitions, and references to default ConfigMaps.

      • clusterinstance-defaults-v1.yaml is a ConfigMap containing default values for cluster installation parameters such as network configuration, image sets, and node settings. The ProvisioningRequest can override or supplement these values with site-specific parameters.

      • policytemplates-defaults-v1.yaml is a ConfigMap containing default values for Day 2 configuration policy parameters such as CPU allocation, hugepages, and SR-IOV settings.

      • extra-manifest/ contains additional manifests applied during cluster installation.

    • policytemplates/ contains PolicyGenerator CRs that define Day 2 configuration policies applied to managed clusters after provisioning:

      • sno-ran-du-pg-v4-Y-Z-v1.yaml is a PolicyGenerator CR that references source CRs and generates the policies enforced on the spoke cluster.

      • source-crs/ contains the source CRs, such as subscriptions, performance profiles, and SR-IOV configurations, referenced by the policy generators.

  2. Create an ArgoCD Application CR for cluster templates that points to the clustertemplates/ directory in your Git repository, for example:

    apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: clusters
  namespace: openshift-gitops
spec:
  destination:
    server: https://kubernetes.default.svc
  project: default
  source:
    path: clustertemplates
    repoURL: https://git.example.com/your-org/ocloud-templates.git
    targetRevision: main
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
  ignoreDifferences:
  - group: metal3.io
    jsonPointers:
    - /spec/preprovisioningNetworkDataName
    - /spec/online
    kind: BareMetalHost

    • spec.source.repoURL specifies the URL of the Git repository containing your cluster templates and configuration resources. Replace with the URL of your repository.

    • spec.source.path points to the clustertemplates/ directory that contains ClusterTemplate CRs, defaults, and hardware profiles.

    • spec.source.targetRevision specifies the Git branch, tag, or commit to track. Set to the branch that contains your production-ready templates.

    • spec.syncPolicy.automated enables automatic synchronization. The prune option removes resources from the cluster that are no longer in Git, and selfHeal reverts manual changes made on the cluster back to the Git-defined state.

    • spec.ignoreDifferences prevents ArgoCD from reverting fields on BareMetalHost CRs that the Bare Metal Operator updates dynamically during provisioning.

  3. Create an ArgoCD Application CR for policy templates that points to the policytemplates/ directory:

    apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: policies
  namespace: openshift-gitops
spec:
  destination:
    server: https://kubernetes.default.svc
  project: default
  source:
    path: policytemplates
    repoURL: https://git.example.com/your-org/ocloud-templates.git
    targetRevision: main
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

    • spec.source.repoURL specifies the URL of the Git repository. This can be the same repository as the cluster templates application if both directories exist in a single repository.

    • spec.source.path points to the policytemplates/ directory that contains Red Hat Advanced Cluster Management (RHACM) policy generator resources and source CRs applied to managed clusters after provisioning.

    • spec.syncPolicy.automated enables automatic synchronization with pruning and self-healing, ensuring the hub cluster always reflects the latest policy definitions from Git.

  4. Apply the ArgoCD application CRs by running the following commands:

    $ oc apply -f <clusters_application_filename>.yaml
$ oc apply -f <policies_application_filename>.yaml

    • Replace <clusters_application_filename>.yaml and <policies_application_filename>.yaml with the names of the application CRs.

Verification

  • Verify that ArgoCD has synchronized the cluster templates to the hub cluster:

    $ oc get clustertemplates.clcm.openshift.io -A

    The output lists the ClusterTemplate CRs with their validation status. A ClusterTemplateValidated condition of True indicates that the template is ready for use.

Configure mTLS for API access

You can configure mutual TLS (mTLS) to require client certificate authentication for all incoming connections to the O-Cloud Manager REST API. This secures API access for any external client, including SMO frameworks, automation platforms, and custom integrations.

Prerequisites

  • The O-Cloud Manager Operator is installed and running on the hub cluster.

  • You have a TLS certificate and private key for the O-Cloud Manager ingress. The certificate must include server auth and client auth extended key usage.

  • You have the CA certificate used to validate incoming client certificates.

Procedure

  1. Create a TLS Secret containing the O-Cloud Manager certificate and private key. The tls.crt field must contain the full certificate chain with the device certificate first, intermediate certificates next, and the root certificate last.

    1. To create the Secret using cert-manager, create a Certificate CR such as the following:

      apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: oran-o2ims-tls-certificate
  namespace: oran-o2ims
spec:
  secretName: oran-o2ims-tls-certificate
  subject:
    organizations:
      - ORAN
  commonName: o2ims.apps.<cluster_domain>
  usages:
    - server auth
    - client auth
  dnsNames:
    - o2ims.apps.<cluster_domain>
  issuerRef:
    name: <issuer_name>
    kind: ClusterIssuer
    group: cert-manager.io

      where:

      <cluster_domain>

      Specifies the hub cluster domain name, for example hub.example.com.

      <issuer_name>

      Specifies the name of your cert-manager ClusterIssuer resource.

    2. Alternatively, to create the Secret manually from existing certificate files, run the following command:

      $ oc create secret tls -n oran-o2ims oran-o2ims-tls-certificate \
  --cert <path_to_cert> \
  --key <path_to_key>

      where:

      <path_to_cert>

      Specifies the path to the full certificate chain file.

      <path_to_key>

      Specifies the path to the private key file.

  2. Create a ConfigMap containing the CA certificates used to validate incoming client certificates by running the following command:

    $ oc create configmap -n openshift-config ingress-client-ca-certs \
  --from-file=ca-bundle.pem=<path_to_client_ca>

    where:

    <path_to_client_ca>

    Specifies the path to the CA certificate file that validates incoming client certificates.

  3. Configure the IngressController to require mTLS for incoming connections by applying the following YAML:

    apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  clientTLS:
    allowedSubjectPatterns:
      - "<subject_pattern>"
    clientCA:
      name: ingress-client-ca-certs
    clientCertificatePolicy: Required

    where:

    <subject_pattern>

    Optional. A regular expression that restricts access to specific certificate subjects, for example ^/O=ORAN/OU=SMO/. Remove the allowedSubjectPatterns field to accept any valid client certificate signed by the configured CA.

    If the ingress controller is shared with other applications, setting clientCertificatePolicy: Required enforces client certificates on all incoming connections. Consider creating a secondary ingress controller for the O-Cloud Manager domain to avoid impacting other applications. Set clientCertificatePolicy: Optional if you cannot enforce mTLS globally but have OAuth enabled.

  4. Update the Inventory CR to reference the TLS certificate by running the following command:

    $ oc patch inventory default -n oran-o2ims --type merge \
  -p '{"spec":{"ingress":{"tls":{"secretName":"oran-o2ims-tls-certificate"}}}}'
Verification

  • Verify that the ingress controller is configured for mTLS by running the following command:

    $ oc get ingresscontroller default -n openshift-ingress-operator \
  -o jsonpath='{.spec.clientTLS}'

    The output shows the configured clientCertificatePolicy, clientCA, and any allowedSubjectPatterns.

Register the O-Cloud Manager with an SMO

Optionally, for telcommunications use cases, you can register the O-Cloud Manager with a Service Management and Orchestration (SMO) system by updating the Inventory custom resource (CR) with the SMO endpoint, OAuth credentials, and CA certificate configuration. Registration is a one-time operation that enables the SMO to manage infrastructure through the O2 IMS REST APIs.

Prerequisites

  • The O-Cloud Manager Operator is installed and running on the hub cluster.

  • You configured mTLS for API access. For more information, see "Configure mTLS for API access".

  • You have the SMO endpoint URL and registration endpoint path.

  • You have OAuth2 client credentials for the O-Cloud Manager, obtained from the OAuth2 authorization server administrator.

  • You have the CA certificate bundle if the SMO or OAuth2 server uses certificates signed by a non-public CA.

Procedure

  1. If the SMO or OAuth2 server TLS certificates are signed by a non-public CA, create a ConfigMap with the CA certificate bundle and configure the cluster proxy by running the following commands:

    $ oc create configmap -n openshift-config <ca_configmap_name> \
  --from-file=ca-bundle.crt=<path_to_ca_bundle>
$ oc patch proxy/cluster --type=merge \
  --patch='{"spec":{"trustedCA":{"name": "<ca_configmap_name>"}}}'

    where:

    <ca_configmap_name>

    Specifies a name for the ConfigMap that stores the CA certificate bundle, for example custom-ca-certs.

    <path_to_ca_bundle>

    Specifies the local file path to the CA certificate bundle that contains the certificates needed to trust the SMO and OAuth2 server endpoints.

    If the cluster proxy already references a custom CA bundle, append the new certificates to the existing bundle rather than replacing it.

  2. Create a ConfigMap with the trust bundle injection label so that the O-Cloud Manager can access both private and public CA certificates:

    apiVersion: v1
kind: ConfigMap
metadata:
  labels:

Authenticate using a service account token

You can authenticate to the O-Cloud Manager REST API by using a service account token. This method is suitable for development, testing, and standalone automation environments that do not require OAuth2 with mutual TLS (mTLS).

Prerequisites

  • You have cluster-admin permissions on the hub cluster.

  • You installed the O-Cloud Manager Operator.

Procedure

  1. Create a service account with API access permissions by running the following commands:

    $ oc create serviceaccount -n oran-o2ims <service_account_name>
    $ oc adm policy add-cluster-role-to-user oran-o2ims-admin-role \
  -n oran-o2ims -z <service_account_name>

    where:

    <service_account_name>

    Specifies a name for the service account used to access the API.

    oran-o2ims-admin-role

    An aggregated cluster role deployed by the Operator that grants read, write, and subscription access to all O-Cloud Manager API endpoints.

  2. Get the base URL for all O-Cloud Manager API requests from the ingress routes by running the following command:

    $ export API_BASE_URL=$(oc get routes -n oran-o2ims -o jsonpath='{.items[0].spec.host}')

  3. Create a scoped bearer token by running the following command:

    $ export MY_TOKEN=$(oc create token -n oran-o2ims <service_account_name> --duration=24h \
  --audience=alarms-server \
  --audience=resource-server \
  --audience=cluster-server \
  --audience=artifacts-server \
  --audience=provisioning-server)

    • The --audience flags scope the token to all O-Cloud Manager API services. Each service validates its own audience claim.

    • The --duration flag sets the token lifetime. Adjust as needed for your environment.

  4. Verify the connection by querying the O-Cloud information endpoint by running the following command:

    $ curl -ks -H "Authorization: Bearer ${MY_TOKEN}" \
  "https://${API_BASE_URL}/O2ims_infrastructureInventory/v2" | jq
Verification

  • A successful response returns O-Cloud metadata including the unique identifier and supported API versions.

Authenticate using OAuth2

In production environments, the O-Cloud Manager REST API supports OAuth2 authentication with mutual TLS (mTLS). This method is used by SMO frameworks and external automation systems that require token-based access. You must acquire a JSON Web Token (JWT) from the OAuth2 authorization server configured in the Inventory custom resource (CR).

Prerequisites

  • The O-Cloud Manager Operator is installed and running on the hub cluster.

  • You configured mTLS for API access. For more information, see "Configure mTLS for API access".

  • You have the TLS client certificate and private key for API access.

  • You have the CA certificate bundle that trusts the OAuth2 server and O-Cloud Manager ingress.

Procedure

  1. Get the base URL for all O-Cloud Manager API requests from the ingress routes by running the following command:

    $ export API_BASE_URL=$(oc get routes -n oran-o2ims -o jsonpath='{.items[0].spec.host}')

  2. Acquire an OAuth2 token from the authorization server by running the following command:

    $ export MY_TOKEN=$(curl -s \
  --cert /path/to/client.crt \
  --key /path/to/client.key \
  --cacert /path/to/ca-bundle.crt \
  -X POST https://<oauth_server_hostname>/realms/<realm>/protocol/openid-connect/token \
  -d grant_type=client_credentials \
  -d client_id=<oauth_client_id> \
  -d client_secret=<oauth_client_secret> \
  -d 'scope=profile openid role:ocloud-manager' | jq -j .access_token)

    where:

    /path/to/client.crt

    Specifies the path to the TLS client certificate. This is the same certificate configured in the Inventory CR’s spec.smo.tls.secretName field.

    /path/to/client.key

    Specifies the path to the TLS private key corresponding to the client certificate.

    /path/to/ca-bundle.crt

    Specifies the path to the CA certificate bundle that trusts the OAuth2 server.

    <oauth_server_hostname>/realms/<realm>

    Specifies the OAuth2 authorization server hostname and realm, matching the spec.smo.oauth.url value in the Inventory CR.

    <oauth_client_id>

    Specifies the OAuth2 client ID for the SMO or API consumer.

    <oauth_client_secret>

    Specifies the corresponding OAuth2 client secret.

  3. Verify the connection by querying the O-Cloud information endpoint by running the following command:

    $ curl -s \
  --cert /path/to/client.crt \
  --key /path/to/client.key \
  --cacert /path/to/ca-bundle.crt \
  -H "Authorization: Bearer ${MY_TOKEN}" \
  "https://${API_BASE_URL}/O2ims_infrastructureInventory/v2" | jq
Verification

  • A successful response returns O-Cloud metadata including the unique identifier and supported API versions.

    When using mTLS, include the --cert, --key, and --cacert flags in all subsequent API requests. If the ingress certificate is signed by a publicly trusted CA, the --cacert flag can be omitted.

Configure hardware profiles for bare-metal nodes

You can optionally define a HardwareProfile custom resource (CR) to specify the required firmware levels and BIOS settings for a class of bare-metal servers. The O-Cloud Manager applies the hardware profile during provisioning to ensure servers meet the required hardware state before cluster installation begins.

Hardware profiles are optional. If you do not specify a hardware profile, the O-Cloud Manager skips firmware and BIOS configuration during provisioning and uses the server in its current hardware state.
Prerequisites

  • The O-Cloud Manager Operator is installed on the hub cluster.

  • You know the target firmware versions and BIOS settings for your server hardware.

Procedure

  1. Create a HardwareProfile CR that defines the required hardware state, such as the following example:

    apiVersion: clcm.openshift.io/v1alpha1
kind: HardwareProfile
metadata:
  name: <hardware_profile_name>
  namespace: oran-o2ims
spec:
  bios:
    attributes:
      BootMode: Uefi
      <bios_attribute_name>: <bios_attribute_value>
  bmcFirmware:
    version: "<bmc_firmware_version>"
    url: "<bmc_firmware_url>"
  biosFirmware:
    version: "<bios_firmware_version>"
    url: "<bios_firmware_url>"
  nicFirmware:
    - version: "<nic_firmware_version>"
      url: "<nic_firmware_url>"

    where:

    <hardware_profile_name>

    Specifies a descriptive name for the hardware profile, for example server-type-bios-settings. The HardwareProfile CR must be created in the O-Cloud Manager Operator namespace, oran-o2ims, regardless of the namespace where the ClusterTemplate CR is stored.

    spec.bios.attributes

    Defines the desired BIOS settings as key-value pairs.

    spec.bmcFirmware

    Defines the target BMC controller firmware. Configure a version and an optional url pointing to the firmware binary.

    spec.biosFirmware

    Defines the target BIOS firmware. Configure a version and an optional url pointing to the firmware binary.

    spec.nicFirmware

    Defines the target NIC firmware as a list, allowing you to specify firmware for multiple NICs. Each entry configures a version and an optional url pointing to the firmware binary.

    All firmware fields are optional. Specify only the components you need to manage. For example, you can define only spec.bios.attributes without any firmware fields if firmware management is not required.

  2. Apply the HardwareProfile resource to the hub cluster, or commit it to the hardwareprofiles/ directory in the GitOps repository for ArgoCD synchronization.

Verification

  • Verify that the HardwareProfile resource exists on the hub cluster:

    $ oc get hardwareprofiles.clcm.openshift.io -A
Onboard bare-metal servers to resource pools

You can register bare-metal servers with the O-Cloud Manager by defining an infrastructure hierarchy and creating BareMetalHost custom resources (CRs) with resource selector labels. Onboarded servers become available for allocation when a ProvisioningRequest CR references a ClusterTemplate CR with matching resource selectors.

Prerequisites

  • The O-Cloud Manager Operator is installed on the hub cluster.

  • You have Baseboard Management Controller (BMC) credentials for each server.

Procedure

  1. Create the infrastructure hierarchy by defining Location, OCloudSite, and ResourcePool CRs, for example:

    apiVersion: ocloud.openshift.io/v1alpha1
# A geographic place. Specify at least one of address, coordinate, or civicAddress.
kind: Location
metadata:
  name: dc1
  namespace: <server_namespace>
spec:
  description: "Data Center 1"
  address: "123 Example Street"
---
apiVersion: ocloud.openshift.io/v1alpha1
# A logical site at a Location. References the parent Location by name.
kind: OCloudSite
metadata:
  name: site-rack-a
  namespace: <server_namespace>
spec:
  description: "Rack A at Data Center 1"
  globalLocationName: dc1
---
apiVersion: ocloud.openshift.io/v1alpha1
# A group of bare-metal resources at a site. References the parent OCloudSite by name.
kind: ResourcePool
metadata:
  name: <resource_pool_name>
  namespace: <server_namespace>
spec:
  description: "<resource_pool_description>"
  oCloudSiteName: site-rack-a

    where:

    <server_namespace>

    Specifies the namespace where server and infrastructure resources are stored. The recommended convention is one namespace per resource pool.

    <resource_pool_name>

    Specifies a descriptive name for the resource pool, for example compute-pool-1.

    <resource_pool_description>

    Describes the purpose or hardware type of the resource pool.

  2. Create a Secret CR containing the BMC credentials for the server, for example:

    apiVersion: v1
kind: Secret
metadata:
  name: <bmc_secret_name>
  namespace: <server_namespace>
type: Opaque
data:
  username: <base64_encoded_username>
  password: <base64_encoded_password>

    where:

    <bmc_secret_name>

    Specifies the name of the secret. This name is referenced by the BareMetalHost resource.

    <base64_encoded_username>

    Specifies the Base64-encoded BMC username.

    <base64_encoded_password>

    Specifies the Base64-encoded BMC password.

  3. Create a BareMetalHost CR with the required labels to associate the server with a resource pool, for example:

    apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: <server_name>
  namespace: <server_namespace>
  labels:
    resources.clcm.openshift.io/resourcePoolName: <resource_pool_name>
    interfacelabel.clcm.openshift.io/boot-interface: <boot_interface_name>
    resourceselector.clcm.openshift.io/server-type: <server_type>
    resourceselector.clcm.openshift.io/rack-location: rack-a-row-3
  annotations:
    bmac.agent-install.openshift.io/allow-provisioned-host-management: ""
spec:
  online: false
  bmc:
    address: redfish-virtualmedia+https://192.168.1.100/redfish/v1/Systems/System.Embedded.1
    credentialsName: <bmc_secret_name>
    disableCertificateVerification: true

    where:

    <server_name>

    Specifies a unique name for the BareMetalHost resource.

    <server_namespace>

    Specifies the namespace where server resources are stored. The recommended convention is one namespace per resource pool.

    resources.clcm.openshift.io/resourcePoolName

    Required. Must match an existing ResourcePool resource’s metadata.name. Links this server to the infrastructure hierarchy. Without this label, the server does not appear in the O-Cloud Manager inventory.

    interfacelabel.clcm.openshift.io/boot-interface

    Required if spec.bootMACAddress is not set. Specifies the physical NIC name used for booting, for example ens3f0. The O-Cloud Manager uses this label to resolve the boot MAC address from hardware inventory data.

    resourceselector.clcm.openshift.io/server-type

    Optional. You can create any labels with the resourceselector.clcm.openshift.io/ prefix to classify servers by hardware type, rack location, or other site-specific criteria. These labels are matched against the resourceSelector criteria in the ClusterTemplate CR during host selection.

    bmac.agent-install.openshift.io/allow-provisioned-host-management

    Optional. Allows the O-Cloud Manager to manage a host that is already in a provisioned state. The O-Cloud Manager sets this annotation automatically during node allocation if not already present.

    spec.online: false

    Prevents the server from being powered on before provisioning. The O-Cloud Manager manages power state during provisioning.

    spec.bmc.address

    Specifies the BMC connection URL in the format <protocol>+https://<bmc_ip>/redfish/v1/Systems/<system_id>. Use redfish-virtualmedia for generic Redfish or idrac-virtualmedia for Dell iDRAC.

    spec.bmc.credentialsName

    Specifies the name of the Secret resource containing the BMC credentials created in the previous step.

  4. Apply the CRs to the hub cluster by running the following commands:

    $ oc apply -f <infrastructure_hierarchy_filename>.yaml
$ oc apply -f <bmc_secret_filename>.yaml
$ oc apply -f <baremetalhost_filename>.yaml

    • Replace <infrastructure_hierarchy_filename>.yaml, <bmc_secret_filename>.yaml, and <baremetalhost_filename>.yaml with the names of the files.

      After the BareMetalHost CR is created, the Bare Metal Operator connects to the BMC, inspects the physical hardware, and populates a HardwareData CR with CPU, memory, NIC, and storage details. This data is used for hardware data filtering during resource selection.

Verification

  1. Verify that the infrastructure hierarchy resources are created by running the following commands:

    $ oc get locations.ocloud.openshift.io
$ oc get ocloudsites.ocloud.openshift.io
$ oc get resourcepools.ocloud.openshift.io

  2. Verify that the BareMetalHost CR is registered and inspection is complete by running the following command:

    $ oc get bmh -A

    The server should show a provisioning state of available after inspection completes, indicating it is ready for allocation.

Create a ClusterTemplate CR for single-node cluster provisioning

You can define a ClusterTemplate custom resource (CR) that serves as a reusable blueprint for provisioning clusters. The template specifies the cluster topology, hardware requirements, and default configuration. It also defines a validation schema for the site-specific parameters that site engineers provide in a ProvisioningRequest CR.

A ClusterTemplate CR references ConfigMap resources that contain defaults for cluster installation and Day 2 policy configuration. The ConfigMap CR for cluster installation defaults defines the common configuration across all clusters provisioned with a template, including cluster-level settings and the shared node configuration for each node group.

When a site engineer creates a ProvisioningRequest resource, the O-Cloud Manager merges the site-specific parameters from the request with these defaults to produce the final cluster and policy definitions.

For multi-node clusters with distinct hardware requirements for each node role, see "Create a ClusterTemplate CR for multi-node cluster provisioning".

For advanced hardware selection using hardware data selectors and site-specific overrides, see "Configure advanced hardware management".
Prerequisites

  • The O-Cloud Manager Operator is installed on the hub cluster.

  • The GitOps repository is configured and synchronized with ArgoCD.

  • Bare-metal servers are onboarded to resource pools with appropriate resource selector labels.

  • If firmware or BIOS management is required, HardwareProfile resources are defined.

Procedure

  1. Create a namespace for the ClusterTemplate and its associated resources by running the following command:

    where:

    <template_namespace>

    Specifies the target namespace for the ClusterTemplate resource and associated ConfigMap resources.

Create a ClusterTemplate CR for multi-node cluster provisioning

You can define a ClusterTemplate CR with multiple node groups in the hwMgmtDefaults.nodeGroupData[] field when your cluster topology includes multiple groups of nodes, such as control plane and worker nodes. Each node group can define its own role, hardware profile, and resource selectors, to enable the O-Cloud Manager to allocate hardware independently for each group.

A ClusterTemplate CR references ConfigMap resources that contain defaults for cluster installation and Day 2 policy configuration. The ConfigMap CR for cluster installation defaults defines the common configuration across all clusters provisioned with a template, including cluster-level settings and the shared node configuration for each node group.

When a site engineer creates a ProvisioningRequest resource, the O-Cloud Manager merges the site-specific parameters from the request with these defaults to produce the final cluster and policy definitions.

Provision a cluster using a ProvisioningRequest

You can provision a cluster by creating a ProvisioningRequest custom resource that references a validated ClusterTemplate CR and supplies site-specific parameters. The O-Cloud Manager validates the request, allocates hardware from resource pools, and orchestrates the end-to-end provisioning flow.

Prerequisites

  • You have cluster-admin permissions on the hub cluster.

  • You prepared the O-Cloud Manager environment, including installing the O-Cloud Manager Operator and configuring the GitOps repository.

  • You defined and applied a valid ClusterTemplate CR on the hub cluster.

  • You onboarded bare-metal servers with resource selector labels matching the ClusterTemplate CR requirements.

Procedure

  1. Create a ProvisioningRequest CR that references the ClusterTemplate CR and supplies site-specific parameters:

    apiVersion: clcm.openshift.io/v1alpha1
kind: ProvisioningRequest
metadata:
  name: 123e4567-e89b-12d3-a456-426614174000
spec:
  name: sno1-request
  description: "SNO cluster for site rack-a"
  templateName: sno-ran-du
  templateVersion: v4-Y-Z-1
  templateParameters:
    nodeClusterName: sno1
    oCloudSiteId: site-rack-a
    clusterInstanceParameters:
      clusterName: sno1
      nodeGroups:
        - name: master
          nodeNetwork:
            config:
              dns-resolver:
                config:
                  server:
                    - 192.0.2.22
          nodes:
          - hostName: sno1.example.com
            nodeNetwork:
              interfaces:
                - name: ens3f0
                  addresses:
                    ipv4: ["192.0.2.10/24"]
    policyTemplateParameters:
      cpu-isolated: "2-31"
      cpu-reserved: "0-1,32-33"

    • metadata.name must be a valid UUID. Any attempt to create a ProvisioningRequest CR with an invalid name is rejected by the webhook.

    • spec.templateName and spec.templateVersion identify the ClusterTemplate CR to use.

    • spec.templateParameters.clusterInstanceParameters provides site-specific values that are merged with the values in the ConfigMap CR that define the cluster instance defaults. The merged data is used to render the ClusterInstance CR.

    • nodeGroups[].name must match an existing nodeGroups entry in the ConfigMap CR that defines the cluster instance defaults. The interface name nodeGroups[].nodes[].nodeNetwork.interfaces[].name must also already exist in the defaults.

    • spec.templateParameters.policyTemplateParameters provides site-specific values for Day 2 configuration policies. These values take precedence over the defaults. Specify only values that differ from the defaults.

      You cannot override extraLabels and extraAnnotations keys that are already defined in the clusterinstance-defaults ConfigMap CR at the group or node level. You can only append new keys. All other fields follow standard merge rules where site-specific values take precedence over defaults.

  2. Apply the ProvisioningRequest resource to the hub cluster, or commit it to the GitOps repository for ArgoCD synchronization.

    Each provisioning stage has a default timeout: 90 minutes for hardware provisioning, 90 minutes for cluster installation, and 30 minutes for cluster configuration. You can override these timeouts in the ClusterTemplate by setting hardwareProvisioningTimeout in hwMgmtDefaults, clusterInstallationTimeout in the clusterinstance-defaults ConfigMap, or clusterConfigurationTimeout in the policytemplates-defaults ConfigMap.
Verification

  • Verify that provisioning completes successfully by running the following command:

    $ oc get provisioningrequests.clcm.openshift.io 123e4567-e89b-12d3-a456-426614174000
    Example output
    NAME                                   DISPLAYNAME    AGE   PROVISIONPHASE   PROVISIONDETAILS
123e4567-e89b-12d3-a456-426614174000   sno1-request   71m   fulfilled        The cluster provisioning has completed successfully

    A provisioningPhase of fulfilled indicates that hardware allocation, cluster installation, and configuration are all complete.

Procedure

    <uuid>

              nodeNetwork:
                interfaces:
                  - name: eno1
                    addresses:
                      ipv4: ["192.0.2.12/24"]

Cancel a scaling operation

You can cancel a node removal or node replacement operation by re-adding the removed worker nodes to the ProvisioningRequest custom resource (CR). The O-Cloud Manager detects the cancellation, stops the removal, and uncordons any nodes that were drained. Node addition operations cannot be canceled.

Cancellation is only effective while the hardware manager is still draining the node. Once the node has been fully deprovisioned and BareMetalHost resource deprovisioning has started, the cancellation window has closed. Re-adding the node at that point triggers a new node addition, which waits for the server to finish deprovisioning before re-provisioning the node.
Prerequisites

  • A node removal or node replacement operation is in progress on the ProvisioningRequest CR.

  • The removed nodes have not yet been fully deprovisioned.

    <uuid>

    Specifies the UUID of the ProvisioningRequest CR for the target cluster.

Template reuse strategies

Every ClusterTemplate CR defines base hardware requirements in its hwMgmtDefaults section, including node groups, roles, and resource selectors that the O-Cloud Manager uses to automatically select hosts from the available pool. When you deploy the same template across multiple sites, you can use the following approaches for handling hardware variation.

Define hardware selection in the template

Use the hwMgmtDefaults section of the ClusterTemplate CR to specify node groups and resource selectors. This is the base configuration that applies to all clusters provisioned with this template. You can use label selectors, hardwaredata/ selectors, or both to match hosts. For details, see "Select hosts by hardware specifications".

Override template defaults for each site

Use this approach when deployments share the same cluster topology, Red Hat OpenShift Container Platform release version, and Day 2 configuration policies but differ in hardware at each site, such as server model, firmware profile, or rack location. The ProvisioningRequest CR supplies site-specific values in hwMgmtParameters that override the ClusterTemplate CR’s hwMgmtDefaults at provisioning time. This avoids creating a separate template for every site. For details, see "Override hardware profiles for each deployment site".

Create a new ClusterTemplate CR

Use this approach when deployments differ in cluster topology (single-node versus multi-node), node count, Red Hat OpenShift Container Platform release version, or Day 2 policy configuration. These structural differences require a separate template because they affect installation flow, ConfigMap defaults, or policy rendering beyond what hardware overrides can address.

ClusterTemplate CRs and their referenced ConfigMap CRs are immutable after validation by the O-Cloud Manager. To change hwMgmtDefaults or any other template default, you must create a new ClusterTemplate CR version and update the ProvisioningRequest CR to reference it.
Select hosts by hardware specifications

You can define the base hardware selection criteria in a ClusterTemplate CR using the resourceSelector field in hwMgmtDefaults specification.

The resourceSelector field supports both label selectors that match BareMetalHost CR labels and hardwaredata/ selectors that match against the inspected HardwareData CR for physical characteristics such as CPU, memory, NICs, and storage devices. You can use either or both together. This base configuration applies to all clusters provisioned with this template unless overridden with the hwMgmtParameters field in the ProvisioningRequest CR.

Prerequisites

  • The O-Cloud Manager Operator is installed on the hub cluster.

  • Bare-metal servers are onboarded and their HardwareData CRs are populated by Bare Metal Operator inspection.

  • If your template references HardwareProfile CRs, those CRs must exist in the O-Cloud Manager Operator namespace ,oran-o2ims, regardless of the namespace where the ClusterTemplate CR is stored.

Procedure

  1. Define the resourceSelector in your ClusterTemplate CR’s hwMgmtDefaults.nodeGroupData[] entry to include hardware data criteria. The following example selects hosts with at least 64 CPU threads, 128 GiB RAM, four 25 Gbps NICs, and two NVMe storage devices:

    # ...
spec:
  templateDefaults:
    hwMgmtDefaults:
      nodeGroupData:
        - name: controller
          role: master
          resourceSelector:
            server-type: dell-xr8620t
            hardwaredata/cpu_model;substring;icase: "Xeon"
            hardwaredata/num_threads;gte: "64"
            hardwaredata/ramMebibytes;gte: "131072"
            hardwaredata/nics;speedGbps>=25;count>=4: "present"
            hardwaredata/storage;type==NVME;count>=2: "present"
# ...

    where:

    server-type: dell-xr8620t

    A label selector. Short keys without a domain prefix are automatically expanded to resourceselector.clcm.openshift.io/server-type. The label must exist on the BareMetalHost CR’s metadata.labels. You can use fully qualified keys such as resourceselector.clcm.openshift.io/server-colour directly.

    hardwaredata/cpu_model;substring;icase: "Xeon"

    A string field selector with qualifiers. The hardwaredata/ prefix indicates matching against the HardwareData CR. Available string fields:

    • productname - system product name

    • manufacturer - system manufacturer

    • cpu_arch - CPU architecture such as x86_64 or arm64

    • cpu_model - CPU model string

    hardwaredata/num_threads;gte: "64"

    An integer field selector with a comparison operator. Available integer fields:

    • num_threads - CPU thread count

    • ramMebibytes - RAM size in mebibytes

      All values must be quoted strings.

    hardwaredata/nics;speedGbps>=25;count>=4: "present"

    A NIC compound selector. NIC criteria use the hardwaredata/nics prefix followed by semicolon-separated sub-criteria. The value must always be "present". Available NIC sub-criteria:

    • model - NIC model string

    • speedGbps - NIC speed in Gbps

    • count - number of NICs matching the other sub-criteria

      When model or speedGbps are specified, they filter the NIC set first. The count sub-criterion is then evaluated against the filtered subset.

    hardwaredata/storage;type==NVME;count>=2: "present"

    A storage compound selector. Storage criteria use the hardwaredata/storage prefix followed by semicolon-separated sub-criteria. The value must always be "present". Available storage sub-criteria:

    • type - storage type: NVME, SSD, or HDD

    • model - device model string

    • vendor - device vendor string

    • name - device name or alternate name

    • sizeBytes - device size in bytes

    • count - number of devices matching the other sub-criteria

      All criteria within a resourceSelector must match for a BareMetalHost CR to be selected. Only hosts in the Available provisioning state are evaluated.

  2. Apply the ClusterTemplate CR to the hub cluster, or commit it to the GitOps repository for ArgoCD synchronization.

Verification

  • Verify that the ClusterTemplate passes validation by running the following command:

    $ oc get clustertemplates.clcm.openshift.io -A

    A STATE of Completed confirms that the template and its resource selector configuration are valid.

Override hardware profiles for each deployment site

When deployments share the same cluster topology but differ in hardware at each site, you can use a single ClusterTemplate CR across multiple deployment sites by overriding the template’s hwMgmtDefaults in each ProvisioningRequest CR. The hwMgmtParameters field in the ProvisioningRequest supplies site-specific values such as server model, firmware profile, or resource selector criteria, which avoids creating a separate template for every site.

Prerequisites

  • The O-Cloud Manager Operator is installed on the hub cluster.

  • A validated ClusterTemplate CR exists with hwMgmtParameters defined in its templateParameterSchema.

  • Bare-metal servers at the target site are onboarded with labels matching the override criteria.

Procedure

  1. Ensure the ClusterTemplate CR includes hwMgmtParameters in the templateParameterSchema to permit overrides. The following snippet shows the required schema section for this example:

    # ...
spec:
  templateParameterSchema:
    properties:
      hwMgmtParameters:
        properties:
          hardwareProvisioningTimeout:
            type: string
          nodeGroupData:
            items:
              properties:
                name:
                  type: string
                hwProfile:
                  type: string
                resourceSelector:
                  type: object
                  additionalProperties:
                    type: string
              required:
                - name
              type: object
            type: array
        type: object
# ...

    The hwMgmtParameters schema defines which fields a ProvisioningRequest CR can override. Only fields declared in the schema are accepted during validation.

  2. Create a ProvisioningRequest CR that includes hwMgmtParameters in templateParameters to override the template defaults for this site, for example:

    apiVersion: clcm.openshift.io/v1alpha1
kind: ProvisioningRequest
metadata:
  name: a1b2c3d4-e5f6-7890-abcd-ef1234567890
spec:
  name: site-boston-rack3
  description: "Cluster for Boston site using local server model"
  templateName: sno-ran-du
  templateVersion: v4-Y-Z-1
  templateParameters:
    nodeClusterName: boston-sno1
    oCloudSiteId: site-boston-rack3
    hwMgmtParameters:
      hardwareProvisioningTimeout: "120m"
      nodeGroupData:
        - name: controller
          hwProfile: rh-profile-xr8620t-bios-settings
          resourceSelector:
            server-type: dell-xr8620t
    clusterInstanceParameters:
      clusterName: boston-sno1
      baseDomain: boston.example.com
      nodes:
        - hostName: boston-sno1.boston.example.com
    policyTemplateParameters:
      cpu-isolated: "2-63"
      cpu-reserved: "0-1"

    where:

    hwMgmtParameters.hardwareProvisioningTimeout

    Overrides the timeout duration for hardware provisioning at this site. If not specified, the value from the ClusterTemplate CR’s hwMgmtDefaults section applies.

    hwMgmtParameters.nodeGroupData[].name

    Identifies the node group to override. This value must match the name field of a node group in the template’s hwMgmtDefaults.nodeGroupData[]. Node groups are matched by name.

    hwMgmtParameters.nodeGroupData[].hwProfile

    Overrides the HardwareProfile CR for this node group at this site. For example, a site with Dell XR8620t servers uses a different firmware profile than a site with HPE DL110 servers.

    hwMgmtParameters.nodeGroupData[].resourceSelector

    Overrides or adds resource selector criteria for this node group. The O-Cloud Manager merges these values with the base selectors from the ClusterTemplate CR using the following rules:

    • Override values replace existing values for the same key.

    • New keys in the override are added to the base configuration.

    • Existing keys not present in the override are preserved unchanged.

    • Keys cannot be removed from the base template through an override.

      When both the ClusterTemplate CR and the ProvisioningRequest CR specify the same field, the ProvisioningRequest value takes precedence.

      Node groups in the override that do not match any existing group by name are appended as new groups. This supports scaling scenarios where a ProvisioningRequest CR adds a worker node group not defined in the template defaults.

  3. Apply the ProvisioningRequest CR to the hub cluster, or commit it to the GitOps repository for ArgoCD synchronization.

Verification

  • Verify that the provisioning request is accepted and progressing by running the following command:

    $ oc get provisioningrequests.clcm.openshift.io a1b2c3d4-e5f6-7890-abcd-ef1234567890

    A provisioningPhase of fulfilled indicates that the overridden hardware profile and resource selector were applied successfully and the cluster provisioning completed.

Update ClusterInstance defaults with template versioning

When cluster-wide installation defaults need to change, for example updating NTP servers or base networking configuration across the fleet, you can update the ClusterInstance defaults for a provisioned cluster by creating a new version of the defaults ConfigMap resource, a new ClusterTemplate custom resource referencing it, and then updating the ProvisioningRequest CR to reference the new template version. Because ClusterTemplate CRs and their referenced ConfigMap CRs are immutable after validation, each change requires new versions of these resources. This approach preserves the previous configuration as a versioned artifact.

Some ClusterInstance fields are immutable after cluster installation. The SiteConfig Operator rejects changes to fields protected by webhooks from underlying Operators. Editable fields include extra labels, extra annotations, and similar metadata.
Prerequisites

  • The cluster is fully provisioned with provisioningPhase: fulfilled on the ProvisioningRequest CR.

  • The GitOps repository is configured and ArgoCD synchronizes resources to the hub cluster.

Procedure

  1. Create a new version of the ClusterInstance defaults ConfigMap resource with the desired updates:

    apiVersion: v1
kind: ConfigMap
metadata:
  name: clusterinstance-defaults-v2
  namespace: <template_namespace>
data:
  clusterinstance-defaults: |
    clusterImageSetNameRef: "4.Y.Z"
    extraAnnotations:
      ManagedCluster:
        new-annotation: "value"

    where:

    <template_namespace>

    Specifies the namespace where ClusterTemplate CRs and associated ConfigMap resources are stored.

    • Update the metadata.name to a new version identifier (for example, clusterinstance-defaults-v2).

    • Modify only the fields you want to change in the data.clusterinstance-defaults section.

  2. Create a new ClusterTemplate CR version referencing the updated ConfigMap resource:

    apiVersion: clcm.openshift.io/v1alpha1
kind: ClusterTemplate
metadata:
  name: sno-ran-du.v4-Y-Z-2
  namespace: <template_namespace>
spec:
  name: sno-ran-du
  version: v4-Y-Z-2
  release: "4.Y.Z"
  templateDefaults:
    clusterInstanceDefaults: clusterinstance-defaults-v2
    policyTemplateDefaults: policytemplates-defaults-v1
    hwMgmtDefaults:
      nodeGroupData:
        - name: controller
          role: master
          resourceSelector:
            server-type: <server_type>

    • Update metadata.name and spec.version to the new version.

    • Set spec.templateDefaults.clusterInstanceDefaults to reference the new ConfigMap resource.

    • The hwMgmtDefaults and policyTemplateDefaults sections must match the original ClusterTemplate CR.

  3. Commit the new resources to the GitOps repository and wait for ArgoCD to synchronize them to the hub cluster.

  4. Update the ProvisioningRequest CR to reference the new ClusterTemplate version by running the following command:

    $ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \

Update firmware and BIOS settings on running clusters

When you need to update firmware patches, or when performance tuning demands updated BIOS settings such as enabling or disabling hyperthreading, you can update firmware versions and BIOS settings on a provisioned cluster by creating a new HardwareProfile custom resource (CR) and updating the ProvisioningRequest CR to reference it. The O-Cloud Manager coordinates a rolling update across node groups, applying changes with minimal workload disruption.

The Day 2 firmware update differs from Day 0 provisioning in the following ways:

  • Node groups are processed by role: control-plane nodes are updated serially first, then worker nodes.

  • Worker nodes can be updated in parallel based on the maxUnavailable setting from the corresponding MachineConfigPool on the spoke cluster.

  • On multi-node clusters, each node is cordoned and drained before firmware is applied. On single-node Red Hat OpenShift Container Platform clusters, cordon and drain are skipped.

Prerequisites

  • The cluster is fully provisioned with provisioningPhase: fulfilled on the ProvisioningRequest CR.

  • The ClusterTemplate CR defines hwMgmtParameters in its spec.templateParameterSchema to accept hardware profile overrides.

  • No other firmware update or upgrade operation is in progress.

  • The firmware download URLs in the new HardwareProfile CR are accessible from the BMC management network.

  • Optional: Adjust the maxUnavailable setting on the worker MachineConfigPool on the spoke cluster to control how many worker nodes are updated in parallel.

Procedure

  1. Create a new HardwareProfile CR with the desired firmware versions and BIOS settings:

    apiVersion: clcm.openshift.io/v1alpha1
kind: HardwareProfile
metadata:
  name: <new_hardware_profile_name>
  namespace: oran-o2ims
spec:
  bios:
    attributes:
      BootMode: Uefi
      WorkloadProfile: HpcProfile
  bmcFirmware:
    version: "<target_bmc_version>"
  biosFirmware:
    version: "<target_bios_version>"

    where:

    <new_hardware_profile_name>

    Specifies a descriptive name for the new hardware profile, such as server-type-bios-2.6.3-bmc-7.20.30.50.

    <target_bios_version>

    Specifies the target BIOS firmware version.

    <target_bmc_version>

    Specifies the target BMC firmware version.

    All firmware fields in the HardwareProfile CR are optional. Specify only the components you need to update. For example, define only spec.bios.attributes without any firmware version fields to update BIOS settings without changing firmware versions.

  2. Apply the new HardwareProfile CR to the hub cluster, or commit it to the GitOps repository for ArgoCD synchronization.

  3. Update the ProvisioningRequest CR to reference the new HardwareProfile by running the following command:

    $ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateParameters":{"hwMgmtParameters":{"nodeGroupData":[{"name":"<node_group>","hwProfile":"<new_hardware_profile_name>"}]}}}}'

    where:

    <uuid>

    Specifies the UUID of the ProvisioningRequest CR for the target cluster.

    <node_group>

    Specifies the node group to update, such as controller or worker.

    <new_hardware_profile_name>

    Specifies the name of the new HardwareProfile CR.

    The O-Cloud Manager detects the profile change and propagates it through the NodeAllocationRequest CR to the hardware manager. The hardware manager computes the firmware differences, updates the Metal3 HostFirmwareSettings and HostFirmwareComponents CRs, and triggers host reboots to apply the updates.

Verification

  • Verify that the firmware update completed successfully by running the following command:

    $ oc get provisioningrequests.clcm.openshift.io <uuid>
    Example output
    NAME                                   DISPLAYNAME   AGE    PROVISIONPHASE   PROVISIONDETAILS
123e4567-e89b-12d3-a456-426614174000                 150m   fulfilled        Provisioning request has completed successfully

    The provisioningPhase returns to fulfilled after all nodes have been updated and validated.

Troubleshooting

  • If the provisioningPhase shows failed, identify which node encountered an error by running the following command:

    $ oc get allocatednodes.clcm.openshift.io -A \
  -o custom-columns=NAME:.metadata.name,REASON:.status.conditions[*].reason,MSG:.status.conditions[*].message

    A node with reason: Failed or reason: TimedOut indicates the node that requires attention. Check the corresponding HostFirmwareComponents and HostFirmwareSettings CRs on the affected BareMetalHost for further details.

Retry a failed configuration change

When a Day 2 configuration change fails due to transient issues such as network connectivity, policy rendering errors, or firmware download timeouts, you can retry the operation by updating the ProvisioningRequest custom resource (CR) specifications. The O-Cloud Manager detects the change and starts a new configuration attempt.

Configuration timeouts and failures can be retried by updating the relevant fields in the ProvisioningRequest CR. However, provisioning timeouts and failures cannot be retried. If a provisioning timeout or failure occurs, the ProvisioningRequest CR must be deleted and recreated.
Prerequisites

  • A Day 2 configuration change on the ProvisioningRequest CR has failed or timed out (HardwareConfigured or ConfigurationApplied condition shows reason: TimedOut or reason: Failed).

Procedure

  1. Check the status conditions by running the following command:

    $ oc get provisioningrequests.clcm.openshift.io <uuid> -o yaml

    where:

    <uuid>

    Specifies the UUID of the ProvisioningRequest CR for the target cluster.

    Look for the HardwareConfigured or ConfigurationApplied condition with reason: TimedOut or reason: Failed and review the message field for details.

  2. For hardware configuration failures, check the BareMetalHost state before retrying by running the following command:

    $ oc get bmh -n <bmh_namespace>

    where:

    <bmh_namespace>

    Specifies the namespace containing the BareMetalHost resources.

    If a BareMetalHost is in servicing state, wait for it to complete before retrying. If a BareMetalHost is in servicing error state, the retry might not succeed, especially for persistent power management errors.

  3. Update the ProvisioningRequest spec to trigger a new configuration attempt by running the following command:

    $ oc edit provisioningrequests.clcm.openshift.io <uuid>

    Make any spec change to the ProvisioningRequest CR, such as updating the hwMgmtParameters to reference a corrected HardwareProfile CR or adjusting policyTemplateParameters values.

    The O-Cloud Manager increments the internal ConfigTransactionId, clears the terminal state, and starts a new configuration attempt.

Verification

  • Verify that the configuration attempt succeeds by monitoring the relevant condition by running the following command:

    $ oc get provisioningrequests.clcm.openshift.io <uuid> -w

    The provisioningPhase transitions from failed to pending to progressing and back to fulfilled on successful completion.

Update cluster configuration with the Provisioning API

You can update Day 2 configuration on a provisioned cluster through the Provisioning REST API by sending an update request with modified policyTemplateParameters values. This method is used by SMO frameworks and external automation systems that manage clusters programmatically. To apply new template defaults, you must first create a new ClusterTemplate CR version on the hub cluster because ClusterTemplate CRs and their referenced ConfigMap CRs are immutable after validation.

Prerequisites

  • You authenticated to the O-Cloud Manager REST API and set the MY_TOKEN environment variable.

  • The cluster is fully provisioned with provisioningPhase: fulfilled.

  • If updating template defaults, a new ClusterTemplate CR version with the updated ConfigMap CRs exists and is validated on the hub cluster.

Procedure

  1. Get the O-Cloud Manager API hostname by running the following command:

    $ export API_HOST=$(oc get routes -n oran-o2ims -o jsonpath='{.items[0].spec.host}')

  2. Set the Provisioning API base URL by running the following command:

    $ export PROV_URL="https://${API_HOST}/O2ims_infrastructureProvisioning/v1"

  3. Retrieve the current provisioning request by running the following command:

    $ curl -ks -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" | jq '.provisioningRequestData' > current-request.json

    where:

    <uuid>

    Specifies the UUID of the provisioning request for the target cluster.

  4. Modify the current-request.json file to update the values in templateParameters.policyTemplateParameters. The following example changes CPU allocation parameters:

    {
  "name": "sno1-provisioning-request",
  "description": "SNO RAN DU cluster at site-east-1",
  "provisioningRequestId": "<uuid>",
  "templateName": "sno-ran-du",
  "templateVersion": "v4-Y-Z-1",
  "templateParameters": {
    "nodeClusterName": "sno1",
    "oCloudSiteId": "site-east-1",
    "policyTemplateParameters": {
      "cpu-isolated": "2-63",
      "cpu-reserved": "0-1"
    },
    "clusterInstanceParameters": {
      "clusterName": "sno1",
      "nodeGroups": [ ... ]
    }
  }
}

    • Only parameters defined in the ClusterTemplate CR’s templateParameterSchema are accepted.

    • To apply new template defaults, update templateVersion to reference a new ClusterTemplate version with the updated ConfigMap defaults.

      The PUT request replaces the entire provisioning request. Retrieve the current state first, then send the complete modified payload. Do not send partial updates.

  5. Send the updated provisioning request by running the following command:

    $ curl -ks -X PUT \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" \
  -d @current-request.json | jq
Verification

  • Query the provisioning request status and verify that configuration is applied by running the following command:

    $ curl -ks -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" | jq -r '.status.provisioningPhase'

    The provisioningPhase transitions from progressing to fulfilled when the updated policies are applied on the spoke cluster.

Prepare cluster templates for a new release

Before you can upgrade a cluster, you must create a new ClusterTemplate custom resource (CR) version for the target Red Hat OpenShift Container Platform release. Because ClusterTemplate CRs and their referenced ConfigMap CRs are immutable after validation, upgrading to a new release requires creating new versions of these resources with updated cluster installation defaults, policy templates, and upgrade configuration.

Prerequisites

  • The GitOps repository is configured and ArgoCD synchronizes resources to the hub cluster.

  • The target Red Hat OpenShift Container Platform version is available as a ClusterImageSet on the hub cluster.

  • For multi-node Red Hat OpenShift Container Platform clusters in disconnected environments, you have mirrored the target release payload to your local registry.

  • For single-node OpenShift clusters in disconnected environments, you have mirrored the seed image to your local registry.

Procedure

  1. Create new clustertemplates and policytemplates directories in the GitOps repository for the target release version, following the same directory structure as existing versions:

    clustertemplates/
├── version_4.Y.Z/
│   └── sno-ran-du/
└── version_4.Y.Z+1/        # new release directory
    └── sno-ran-du/

policytemplates/
├── version_4.Y.Z/
│   └── sno-ran-du/
└── version_4.Y.Z+1/        # new release directory
    └── sno-ran-du/

  2. Create a ClusterInstance defaults ConfigMap resource for the new version with the updated clusterImageSetNameRef:

    apiVersion: v1
kind: ConfigMap
metadata:
  name: clusterinstance-defaults-v1
  namespace: <template_namespace>
data:
  clusterinstance-defaults: |
    clusterImageSetNameRef: "<target_version>"
    extraLabels:
      ManagedCluster:
        cluster-version: "<version_label>"
        <template_name>-policy: "v1"

    where:

    <template_namespace>

    Specifies the namespace for the new ClusterTemplate version, such as sno-ran-du-v4-Y-Z+1.

    <target_version>

    Specifies the target Red Hat OpenShift Container Platform version, such as 4.22.0.

    <version_label>

    Specifies a label value identifying the cluster version, such as v4-22-0.

    <template_name>

    Specifies the template name used for policy binding, such as sno-ran-du.

    The remaining configuration in the cluster instance defaults ConfigMap CR must remain identical to the original ConfigMap CR used for provisioning. For example, the extraManifestsRefs field must reference the same ConfigMap CR as the original version.

  3. Create policy templates for the new version with updated Operator index images and any new configuration manifests.

  4. Create the ClusterTemplate CR for the target release with upgrade configuration. The upgradeDefaults section differs depending on the cluster topology:

    1. For single-node Red Hat OpenShift Container Platform clusters, configure the upgradeDefaults section with imageBasedGroupUpgrade specifications, and include the upgradeParameters schema to enable cluster overrides:

    clusterInstanceDefaults: clusterinstance-defaults-v1

            rolloutStrategy:
              maxConcurrency: 1

            rolloutStrategy:
              maxConcurrency: 1
              timeout: 60
          - actions: ["AbortOnFailure"]

            type: object

                properties:
                  autoRollbackOnFailure:
                    properties:
                      initMonitorTimeoutSeconds:
                        minimum: 0
                        type: integer
                    type: object
                  oadpContent:
                    items:
                      properties:
                        name:
                          type: string
                        namespace:
                          type: string
                      type: object
                    type: array
                  seedImageRef:
                    properties:
                      image:
                        minLength: 1
                        type: string
                      pullSecretRef:
                        properties:
                          name:
                            type: string
                        type: object
                      version:
                        type: string
                    type: object
                type: object
              plan:
                items:
                  properties:
                    actions:
                      items:
                        type: string
                      maxItems: 4
                      type: array

                      properties:

                          type: integer
                        timeout:
                          type: integer
                      type: object

      - nodeClusterName
      - oCloudSiteId
      - policyTemplateParameters
      - clusterInstanceParameters
    type: object

      where:

      <template_name>

      Specifies the base template name, such as sno-ran-du.

      <template_namespace>

      Specifies the namespace for the new ClusterTemplate version.

      <target_version>

      Specifies the target Red Hat OpenShift Container Platform version.

      <version_label>

      Specifies the version label used in the OADP backup ConfigMap CR, such as v4-Y-Z+1-1.

      spec.templateDefaults.upgradeDefaults

      Defines the default upgrade configuration for image-based upgrades on single-node OpenShift clusters.

      ibuSpec.seedImageRef

      Specifies the seed container image and target platform version for the upgrade.

      For disconnected environments, the spoke cluster cannot reach public registries. You must set ibuSpec.seedImageRef.image to the mirrored seed image in your local registry, for example:

      - oCloudSiteId

      - clusterInstanceParameters
    type: object

      where:

      <template_name>

      Specifies the base template name, such as std-ran-du.

      <template_namespace>

      Specifies the namespace for the new ClusterTemplate version.

      <target_version>

      Specifies the target Red Hat OpenShift Container Platform version.

      spec.templateDefaults.upgradeDefaults

      Defines the default upgrade configuration for standard platform upgrades on multi-node clusters.

      clusterVersion.cvSpec.channel

      Specifies the update channel for the target release.

      clusterVersion.cvSpec.desiredUpdate.version

      Specifies the target Red Hat OpenShift Container Platform version.

      Defines the maximum time allowed for the upgrade to complete.

    $ oc get provisioningrequests.clcm.openshift.io <uuid> \

    The reason field categorizes the failure: TimedOut indicates the upgrade exceeded the configured timeout, PreconditionChecksFailed indicates unmet requirements such as schema validation or version mismatch, and Failed indicates a runtime error. The message field provides specific details about the cause.

Override upgrade parameters for a ProvisioningRequest

You can override the default upgrade parameters defined in the ClusterTemplate custom resource (CR) by specifying upgradeParameters in the ProvisioningRequest CR. Override values are merged with the values you defined in the upgradeDefaults field of the ClusterTemplate CR, with the values specified in the ProvisioningRequest CR taking precedence.

For image-based upgrades, the plan field is an array and is merged by index position. Element 0 of the override merges with element 0 of the defaults, element 1 with element 1, and so on.

Both upgradeDefaults in the ClusterTemplate CR and upgradeParameters in the ProvisioningRequest CR must conform to the templateParameterSchema schema defined in the ClusterTemplate CR. Invalid overrides are rejected during validation.
Prerequisites

  • A ClusterTemplate CR is prepared for the target release with upgradeDefaults configured.

  • The templateParameterSchema in the ClusterTemplate CR exposes the upgradeParameters sub-schema.

Procedure

  1. Edit the ProvisioningRequest CR to add or update the spec.templateParameters.upgradeParameters field by running the following command:

    $ oc edit provisioningrequests.clcm.openshift.io <uuid>

    where:

    <uuid>

    Specifies the UUID of the ProvisioningRequest CR for the target cluster.

    1. For single-node image-based upgrades, you can override any upgrade parameter defined in the templateParameterSchema. The following example overrides the seed image and stage timeouts:

      spec:
  templateParameters:
    upgradeParameters:
      imageBasedGroupUpgrade:
        ibuSpec:
          seedImageRef:
            image: "quay.io/seed-repo/seed-image:4.Y.Z+1-v2"
        plan:
          - actions: ["Prep"] # index 0
            rolloutStrategy:
              timeout: 20
          - actions: ["AbortOnFailure"] # index 1
          - actions: ["Upgrade"] # index 2
            rolloutStrategy:
              timeout: 90

      • seedImageRef.image overrides the seed image to use a different image tag.

      • rolloutStrategy.timeout sets the Prep stage timeout to 20 minutes and the Upgrade stage timeout to 90 minutes.

      • Fields not specified in upgradeParameters are inherited from the upgradeDefaults field of the ClusterTemplate CR.

        During an in-progress image-based upgrade, all parameter changes are ignored until the upgrade completes or fails.

    2. For multi-node standard platform upgrades, you can override any upgrade parameter defined in the templateParameterSchema. The following example overrides the timeout and channel specifications:

      spec:
  templateParameters:
    upgradeParameters:
      clusterVersion:
        clusterUpgradeTimeout: "6h"
        cvSpec:
          channel: "eus-4.22"

      During an in-progress upgrade, only clusterVersion.clusterUpgradeTimeout is recognized as an update. Other parameter changes are ignored until the upgrade completes or fails.

  2. Apply the updated ProvisioningRequest CR to the hub cluster, or commit it to the GitOps repository for ArgoCD synchronization.

Verification

  • Verify that the override is accepted by checking that the upgrade proceeds with the modified parameters by running the following command:

    $ oc get provisioningrequests.clcm.openshift.io <uuid> -o jsonpath='{.status.conditions[?(@.type=="UpgradeCompleted")]}'
Retry a failed single-node OpenShift cluster upgrade

When an image-based upgrade fails on a single-node OpenShift cluster, the recovery path depends on the failure reason reported in the UpgradeCompleted condition. Input errors can be corrected in place, while runtime failures require reverting to the original ClusterTemplate version after the automatic rollback completes.

Prerequisites

  • The UpgradeCompleted condition on the ProvisioningRequest CR shows reason: PreconditionChecksFailed, reason: Failed, or reason: TimedOut.

Procedure

  1. Check the UpgradeCompleted condition to determine the failure type by running the following command:

    $ oc get provisioningrequests.clcm.openshift.io <uuid> \
  -o jsonpath='{.status.conditions[?(@.type=="UpgradeCompleted")]}'

    where:

    <uuid>

    Specifies the UUID of the ProvisioningRequest CR for the target cluster.

  2. If the reason is PreconditionChecksFailed, fix the input error directly:

    The upgrade was not started because a precondition was not met, such as a schema validation failure or version mismatch. Patch the ProvisioningRequest CR with corrected upgradeParameters or fix the referenced ClusterTemplate CR. The O-Cloud Manager re-evaluates the upgrade automatically after the change is detected.

  3. If the reason is TimedOut or Failed, wait for the automatic rollback to complete and then retry:

    1. Wait for the automatic rollback to complete. The ImageBasedGroupUpgrade plan includes AbortOnFailure actions that handle rollback and cleanup automatically.

    2. Revert the ProvisioningRequest CR to the original ClusterTemplate version by running the following command:

      $ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<original_version>"}}'

      where:

      <template_name>

      Specifies the template name, such as sno-ran-du.

      <original_version>

      Specifies the original ClusterTemplate version, such as v4-Y-Z-1.

    3. Wait for the ProvisioningRequest CR to return to provisioningPhase: fulfilled.

    4. Investigate and resolve the root cause of the failure based on the message field from the UpgradeCompleted condition, such as a network timeout or seed image issue.

    5. Re-trigger the upgrade by updating the ProvisioningRequest CR to the target ClusterTemplate version by running the following command:

      $ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<target_version>"}}'

      where:

      <target_version>

      Specifies the new ClusterTemplate version for the target release.

Verification

  1. Verify that the upgrade completed successfully by running the following command on the hub cluster:

    $ oc get provisioningrequests.clcm.openshift.io <uuid>
    Example output
    NAME                                   DISPLAYNAME   AGE    PROVISIONPHASE   PROVISIONDETAILS
123e4567-e89b-12d3-a456-426614174000                 240m   fulfilled        Upgrade is completed

  2. Verify the upgrade progress on the spoke cluster by running the following commands:

    1. Get the status of the upgrade by running the following command:

      $ oc get ibu

    2. Get the status of the machine config pools by running the following command:

      $ oc get mcp
Retry a failed multi-node cluster upgrade

When a standard platform upgrade fails on a multi-node Red Hat OpenShift Container Platform cluster, the recovery path depends on the failure reason reported in the UpgradeCompleted condition. Input errors can be corrected in place, while timeout failures require investigating the spoke cluster and determining whether to retry or reconcile a manually completed upgrade.

Prerequisites

  • The UpgradeCompleted condition on the ProvisioningRequest CR shows reason: PreconditionChecksFailed, or reason: TimedOut.

  • You have access to the spoke cluster for investigation if the failure reason is TimedOut.

Procedure

  1. Check the UpgradeCompleted condition to determine the failure type by running the following command:

    $ oc get provisioningrequests.clcm.openshift.io <uuid> \
  -o jsonpath='{.status.conditions[?(@.type=="UpgradeCompleted")]}'

    where:

    <uuid>

    Specifies the UUID of the ProvisioningRequest CR for the target cluster.

  2. If the reason is PreconditionChecksFailed, fix the input error directly:

    The upgrade was not started or was rejected because a precondition was not met, such as a schema validation failure, version mismatch, or invalid ClusterVersion configuration. Patch the ProvisioningRequest CR with corrected upgradeParameters values or fix the referenced ClusterTemplate CR. The O-Cloud Manager re-evaluates the upgrade automatically after the change is detected.

  3. If the reason is TimedOut, investigate the spoke cluster to determine the root cause. Check the UpgradeCompleted condition message for details, which might include Cluster Version Operator conditions such as Failing or Upgradeable=False.

  4. Resolve the root cause on the spoke cluster, such as fixing a degraded Operator or clearing a misconfigured policy.

  5. Revert the ProvisioningRequest CR to the original ClusterTemplate version by running the following command:

    $ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<original_version>"}}'

    where:

    <template_name>

    Specifies the template name, such as std-ran-du.

    <original_version>

    Specifies the original ClusterTemplate version, such as v4-Y-Z-1.

  6. Wait for the ProvisioningRequest CR to return to provisioningPhase: fulfilled.

  7. Re-trigger the upgrade by updating the ProvisioningRequest CR to the target ClusterTemplate CR version by running the following command:

    $ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<target_version>"}}'

    where:

    <target_version>

    Specifies the new ClusterTemplate CR version for the target release.

    If the administrator completed the upgrade to the target version outside of the O-Cloud Manager, you can skip the revert and re-trigger steps. Instead, add or update a ManagedCluster label through the ProvisioningRequest clusterInstanceParameters to trigger reconciliation:

    $ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateParameters":{"clusterInstanceParameters":{"extraLabels":{"ManagedCluster":{"upgrade-reconcile":"true"}}}}}}'

    The O-Cloud Manager detects that the spoke cluster is already running the target version and transitions the ProvisioningRequest CR to provisioningPhase: fulfilled.
Verification

  1. Verify that the upgrade completed successfully by running the following command on the hub cluster:

    $ oc get provisioningrequests.clcm.openshift.io <uuid>
    Example output
    NAME                                   DISPLAYNAME   AGE    PROVISIONPHASE   PROVISIONDETAILS
123e4567-e89b-12d3-a456-426614174000                 300m   fulfilled        Upgrade to version 4.22.0 completed

  2. Verify the upgrade progress on the spoke cluster by running the following commands:

    1. Get the status of the upgrade by running the following command:

      $ oc adm upgrade

    2. Get the status of the machine config pools by running the following command:

      $ oc get mcp
Upgrade clusters with the Provisioning API

You can trigger a cluster upgrade through the Provisioning REST API by sending an update request with a new templateVersion that references a ClusterTemplate CR configured for the target release. Because ClusterTemplate CRs and their referenced ConfigMap CRs are immutable after validation, a new ClusterTemplate CR version must be prepared for the target release before sending the upgrade request. This method is used by SMO frameworks and external automation systems that manage cluster upgrades programmatically.

Prerequisites

  • You authenticated to the O-Cloud Manager REST API and set the MY_TOKEN environment variable.

  • The cluster is fully provisioned with provisioningPhase: fulfilled.

  • A new ClusterTemplate CR version configured for the target Red Hat OpenShift Container Platform release exists on the hub cluster.

Procedure

  1. Get the O-Cloud Manager API hostname by running the following command:

    $ export API_HOST=$(oc get routes -n oran-o2ims -o jsonpath='{.items[0].spec.host}')

  2. Set the Provisioning API base URL by running the following command:

    $ export PROV_URL="https://${API_HOST}/O2ims_infrastructureProvisioning/v1"

  3. Retrieve the current provisioning request by running the following command:

    $ curl -ks -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" | jq '.provisioningRequestData' > current-request.json

    where:

    <uuid>

    Specifies the UUID of the provisioning request for the target cluster.

  4. Modify the current-request.json file to update the templateVersion field to the new release version. The following example upgrades from version v4-Y-Z-1 to v4-Y-Z+1-1:

    {
  "name": "sno1-provisioning-request",
  "description": "SNO RAN DU cluster at site-east-1",
  "provisioningRequestId": "<uuid>",
  "templateName": "sno-ran-du",
  "templateVersion": "v4-Y-Z+1-1",
  "templateParameters": {
    "nodeClusterName": "sno1",
    "oCloudSiteId": "site-east-1",
    "clusterInstanceParameters": {
      "clusterName": "sno1",
      "nodeGroups": [ ... ]
    },
    "policyTemplateParameters": { ... }
  }
}

    • The templateVersion value must match the version of the new ClusterTemplate CR prepared for the target release.

    • All other fields remain unchanged unless the new template requires different parameter values.

      The PUT request replaces the entire provisioning request. Retrieve the current state first, then send the complete modified payload. Do not send partial updates.

  5. Send the updated provisioning request by running the following command:

    $ curl -ks -X PUT \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" \
  -d @current-request.json | jq
Verification

  • Query the provisioning request status and verify that the upgrade completes by running the following command:

    $ curl -ks -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" | jq -r '.status.provisioningPhase'

    The provisioningPhase transitions from progressing to fulfilled when the upgrade completes successfully.

Manage alarm subscriptions

You can create alarm subscriptions through the O-Cloud Manager Alarms API to receive real-time HTTP notifications when alarm states change. When a subscription is active, the O-Cloud Manager sends callbacks to the specified endpoint whenever a matching alarm event occurs.

Prerequisites

  • You authenticated to the O-Cloud Manager REST API and set the API_BASE_URL and MY_TOKEN environment variables.

  • You configured SMO integration for the O-Cloud Manager. Alarm subscription creation is blocked until the SMO attributes are configured in the Inventory custom resource (CR).

  • Your webhook endpoint is reachable from the hub cluster and responds to GET requests with a 204 status code.

Procedure

  1. Set the Alarms API base URL by running the following command:

    $ export ALARMS_URL="https://${API_BASE_URL}/O2ims_infrastructureMonitoring/v1"

  2. Create an alarm subscription by running the following command:

    $ curl -ks -X POST \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${MY_TOKEN}" \
  -d '{
    "consumerSubscriptionId": "69253c4b-8398-4602-855d-783865f5f25c",
    "filter": "NEW",
    "callback": "https://smo.example.com/v1/alarms"
  }' \
  "${ALARMS_URL}/alarmSubscriptions" | jq

    • consumerSubscriptionId must be a valid UUID identifying this subscription on the consumer side.

    • callback is the URL where the O-Cloud Manager sends alarm notifications.

    • filter specifies which alarm event type to exclude from notifications. If you omit the filter, all alarm events are reported:

      • NEW — Exclude notifications when a new alarm is raised.

      • CHANGE — Exclude notifications when an existing alarm changes, for example a severity change.

      • CLEAR — Exclude notifications when an alarm is cleared.

      • ACKNOWLEDGE — Exclude notifications when an alarm is acknowledged.

      If SMO attributes are not configured in the Inventory CR, subscription creation fails with the error: "provisioning of Alarm Subscriptions is blocked until the SMO attributes are configured."

  3. List all alarm subscriptions by running the following command:

    $ curl -ks -H "Authorization: Bearer ${MY_TOKEN}" \
  "${ALARMS_URL}/alarmSubscriptions" | jq

  4. Delete an alarm subscription by running the following command:

    $ curl -ks -X DELETE \
  -H "Authorization: Bearer ${MY_TOKEN}" \
  "${ALARMS_URL}/alarmSubscriptions/<subscription_id>"

    • Replace <subscription_id> with the subscription identifier returned when the subscription was created.

Verification

  • After creating a subscription, verify it appears in the subscription list. Trigger a test alert on a managed cluster and confirm that your webhook endpoint receives the notification callback.
