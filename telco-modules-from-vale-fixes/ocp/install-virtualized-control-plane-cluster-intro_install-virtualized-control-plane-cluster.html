Install a virtualized control plane cluster

You can plan, prepare, deploy, and manage an Red Hat OpenShift Container Platform cluster with a virtualized control plane, running control plane nodes as virtual machines on a hosting cluster.

Understand virtualized control planes

Learn how virtualized control planes work, including architecture, deployment workflow, and high-availability mechanisms.

How virtualized control planes work

A virtualized control plane deployment involves two distinct clusters:

Hosting cluster

An existing Red Hat OpenShift Container Platform cluster running OpenShift Virtualization that hosts the control plane VMs. A single hosting cluster can support multiple target clusters by running each cluster’s control plane VMs in separate namespaces.

Target cluster

The Red Hat OpenShift Container Platform cluster whose control plane nodes run as VMs on the hosting cluster. The target cluster’s worker nodes run on separate infrastructure, either physical servers or VMs on different hosts.

KubeVirt Redfish runs on the hosting cluster and exposes the control plane VMs through standard Redfish API endpoints. This enables standard installation workflows such as Agent-based Installer, installer-provisioned infrastructure, or GitOps Zero Touch Provisioning (ZTP) to treat the VMs the same as physical servers with baseboard management controllers (BMCs).

Virtualized control planes differ from Hosted control planes. With virtualized control planes, the control plane runs as VMs with hypervisor-level isolation. With Hosted control planes, the control plane runs as pods with container-level isolation.
When to use a virtualized control plane

You can use virtualized control planes to address infrastructure challenges where physical hardware constraints, compliance requirements, or provisioning timelines limit how you deploy and manage clusters.

Regulatory isolation

You must meet compliance mandates that require hypervisor-level isolation for control plane components. A virtualized control plane runs each control plane node as a separate VM, providing stronger isolation boundaries than container-based alternatives.

Infrastructure consolidation

You want to reduce hardware costs by hosting multiple cluster control planes on shared infrastructure. A single hosting cluster can run control plane VMs for multiple target clusters in separate namespaces, reducing the number of physical servers you need to maintain.

Faster cluster provisioning

You need to deploy new clusters faster than physical bare-metal provisioning allows. Provisioning control plane VMs on an existing hosting cluster reduces the lead times associated with physical hardware provisioning.

You can deploy virtualized control planes by using standard installation workflows such as Agent-based Installer, installer-provisioned infrastructure, or GitOps Zero Touch Provisioning (ZTP). These workflows treat the VMs the same as physical servers with baseboard management controllers (BMCs), so your existing deployment processes work without modification.

Virtualized control plane architecture

A single hosting cluster runs control plane VMs for multiple target clusters across its nodes.

The following diagram shows a multitenant virtualized control plane deployment.

The hosting cluster runs each control plane VM as a VirtualMachine CR managed by OpenShift Virtualization. KubeVirt Redfish exposes these VMs through standard Redfish API endpoints, which the installation workflow uses to manage VM power state and boot order.

Each target cluster’s control plane VMs are distributed across hosting cluster nodes by using anti-affinity rules, so that a single node failure affects only one VM for each target cluster. The VMs run in a dedicated namespace on the hosting cluster, providing resource and access isolation between target clusters.

Each target cluster has its own machine network that provides L2 connectivity between its control plane VMs. The target cluster’s worker nodes run on a separate L2 network segment on bare-metal infrastructure, connected to the control plane through routed L3 connectivity. The apiVIPs must reside on the same L2 segment as the control plane VMs, and the ingressVIPs must reside on the same L2 segment as the worker nodes.

Network address translation (NAT) is not supported between the control plane and worker networks.

The following diagram shows how network traffic flows inside a single hosting cluster node. Control plane VM traffic and hosting cluster pod traffic use separate network paths.

Control plane VMs connect to the cluster machine network through a Multus NetworkAttachmentDefinition resource and a secondary bridge interface. Hosting cluster pods use the default OVN-Kubernetes network on a separate bridge and NIC.

Virtualized control plane deployment workflow

A virtualized control plane deployment involves installing KubeVirt Redfish on the hosting cluster, configuring it to expose VMs, and running a supported installation method.

Virtualized control planes require an Red Hat OpenShift Container Platform cluster with OpenShift Virtualization installed and operational, which operates as the hosting cluster.

The following high-level steps outline the deployment process:

  1. Install and configure KubeVirt Redfish on the hosting cluster.

    This includes defining which VMs to expose through the Redfish API, configuring authentication credentials, and creating a Route CR to expose the endpoint externally.

  2. Create the control plane VMs on the hosting cluster.

    Configure the VMs with appropriate resources and network settings, and ensure they remain powered off until the installation begins.

  3. Configure high availability for the control plane VMs.

    Set anti-affinity rules to distribute VMs across different physical nodes, create a PodDisruptionBudget to prevent concurrent eviction, and set the VM eviction strategy to None.

  4. Configure your installation method to use KubeVirt Redfish.

    In your configuration files, specify BMC addresses using the KubeVirt Redfish route URL for the virtualized control plane nodes, for example: redfish-virtualmedia+https://<kubevirt_redfish_route>/redfish/v1/Systems/<vm_namespace>.<vm_name>.

  5. Run the installation.

    The VMs boot from the installation media and communicate with each other to form the cluster. Depending on the installation method, this process is either fully automated or requires manual intervention to boot each node.

    After installation completes, a new Red Hat OpenShift Container Platform cluster is deployed with its control plane running on VMs hosted by the original OpenShift Virtualization cluster.

High availability for virtualized control planes

A virtualized control plane relies on etcd quorum to remain operational. With three control plane VMs, the cluster tolerates the loss of one VM but becomes unavailable if two VMs fail simultaneously.

To protect quorum, distribute VMs across physical nodes and prevent disruptive operations from affecting more than one control plane VM at a time.

Live migration is not supported for virtualized control plane VMs. The eviction strategy for control plane VMs must be set to None to prevent the hosting cluster from attempting to migrate them during node drain operations.
Anti-affinity for virtualized control planes

Anti-affinity rules ensure that control plane VMs are distributed across different physical nodes on the hosting cluster so that a single node failure affects only one control plane VM.

The following methods are available for configuring this placement:

  • Pod anti-affinity rules in the VirtualMachine specification, which prevent multiple control plane VMs from being scheduled on the same node.

  • Topology spread constraints, which evenly distribute VMs across failure domains.

A hosting cluster requires at least three physical nodes to support anti-affinity placement for the three control plane VMs of a target cluster.

Pod disruption budgets for virtualized control planes

A PodDisruptionBudget (PDB) prevents the hosting cluster from evicting more than one control plane VM at a time during node drain or maintenance operations. You can configure a PDB to ensure that at least two control plane VMs remain running, which preserves etcd quorum.

Without a PDB, draining multiple hosting cluster nodes concurrently could evict more than one control plane VM at a time and cause quorum loss.

QEMU guest agent for virtualized control planes

The QEMU guest agent is required on each control plane VM. The hosting cluster uses a readiness probe to ping the guest agent and verify that the VM is healthy. This health check enables the hosting cluster to safely coordinate node drain operations while maintaining etcd quorum.

Without the guest agent, the readiness probe cannot confirm that a VM is healthy, and the pod disruption budget cannot manage drain operations correctly.

Readiness probes for virtualized control planes

Readiness probes verify that the VM operating system and critical services are operational. The hosting cluster uses readiness probe results to determine whether a VM is healthy before allowing operations that affect other VMs in the same target cluster.

Readiness probes work together with pod disruption budgets to ensure that the hosting cluster does not proceed with draining a node until the previously affected control plane VM is confirmed healthy on another node.

Hosting cluster maintenance for virtualized control planes

Hosting cluster maintenance, such as operating system updates or hardware repairs, can disrupt control plane VMs on the affected node. To preserve etcd quorum during these operations, maintenance must follow a sequential, one-node-at-a-time approach.

Before any node is cordoned, all control plane VMs must be healthy and etcd quorum must be intact. Only one hosting cluster node is drained at a time. After the drained node’s control plane VM shuts down, the remaining control plane VMs must still maintain etcd quorum before maintenance proceeds. The node is returned to service and the VM and etcd member are verified healthy before the next node is drained.

Review requirements for virtualized control planes

Review the hosting cluster, storage, network, control plane VM, and KubeVirt Redfish requirements for virtualized control planes.

Hosting cluster requirements

The hosting cluster runs the virtualized control plane VMs and manages their lifecycle through KubeVirt Redfish.

The hosting cluster requires the following components:

  • Red Hat OpenShift Container Platform installed and operational.

  • OpenShift Virtualization installed and configured.

  • Sufficient compute resources to host control plane VMs.

  • At least three physical nodes to enable anti-affinity placement, ensuring control plane VMs are spread across different physical hosts.

Storage requirements

The hosting cluster must have a storage solution that supports VM disk images and meets the latency requirements of etcd.

Use Logical Volume Manager (LVM) Storage backed by NVMe drives for virtualized control plane storage. LVM Storage writes directly to local disks, providing the consistent low latency that etcd requires. Use dedicated NVMe drives for control plane VM disks to ensure predictable performance.

Do not use Red Hat OpenShift Data Foundation (ODF) for control plane VM disk storage. ODF replicates data across multiple storage nodes, which can cause unpredictable latency spikes during synchronization that affect etcd performance.

During installation of the virtualized control plane, KubeVirt Redfish requires a shared storage location for the installation ISO. When the installer mounts boot media through the Redfish API, KubeVirt Redfish creates a data volume, downloads the installation ISO into that volume, and attaches the volume to the VM as virtual media. Because control plane VMs can be scheduled on any worker node in the hosting cluster, the storage location for the installation ISO must be accessible from all nodes. Do not use a node-local storage class such as LVM Storage for this volume.

Network requirements

Virtualized control plane deployments require specific network connectivity between VMs, worker nodes, and external services.

Configure networking to meet the following requirements:

  • L2 network connectivity between control plane VMs. The Red Hat OpenShift Container Platform installation program requires all control plane nodes to share the same L2 network segment. The apiVIPs must reside on this L2 segment.

  • A separate L2 network segment for worker nodes. The ingressVIPs must reside on the same L2 segment.

  • L3 connectivity without network address translation (NAT) between the control plane VMs and worker nodes. Worker nodes must be able to route traffic directly to the control plane VMs. During installation, the bootstrap VM also requires L3 connectivity to the control plane.

  • External access to the cluster API.

  • Access to container image registries.

  • DNS resolution for cluster components.

You can use either dynamic or static IP addressing for the control plane VMs:

  • For deployments that use DHCP, configure static MAC addresses on the primary network interfaces of the VMs and create DHCP reservations for each MAC address. This ensures consistent IP assignment across VM restarts.

  • For deployments that use static IP addressing, define the network configuration in your install-config.yaml or Agent-based installation manifests.

Control plane VM requirements

Each control plane VM must meet minimum resource requirements to run the Red Hat OpenShift Container Platform control plane components reliably.

Each control plane VM requires the following minimum resources:

  • 8 vCPUs

  • 16 GiB RAM

  • 120 GiB storage

    Use Logical Volume Manager (LVM) Storage backed by NVMe drives for virtualized control plane storage.
KubeVirt Redfish requirements

KubeVirt Redfish exposes VMs through the Redfish API.

You need the following to use KubeVirt Redfish:

  • Network access from the installation workstation to the KubeVirt Redfish route.

  • Credentials configured in KubeVirt Redfish for API authentication.

  • VMs labeled to be exposed through the Redfish API.

  • A shared storage location for the installation ISO. During installation of the virtualized control plane, KubeVirt Redfish uses this location to create a data volume, download the installation ISO into that volume, and attach the volume to the VM as virtual media. Because VMs can be scheduled on any worker node in the hosting cluster, this storage location must be accessible from all nodes. Do not use a node-local storage class such as LVM Storage.

Prerequisites

Create control plane VMs

Create VMs on the hosting cluster that will become the control plane nodes for your virtualized control plane cluster.

Prerequisites

  • KubeVirt Redfish is installed and configured on the hosting cluster.

  • The hosting cluster has a network configured to provide Layer 2 connectivity between VMs.

  • Logical Volume Manager (LVM) Storage is installed on the hosting cluster.

Procedure

  1. Create a VirtualMachine CR for each control plane node by creating a YAML file with content such as the following example:

    apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: control-plane-0
  namespace: <vm_namespace>
  labels:
    redfish-enabled: "true"
    vcp-cluster: <cluster_name>
spec:
  runStrategy: Halted
  dataVolumeTemplates:
    - metadata:
        name: control-plane-0-disk
      spec:
        source:
          blank: {}
        storage:
          accessModes:
            - ReadWriteOnce
          volumeMode: Block
          resources:
            requests:
              storage: 120Gi
          storageClassName: <storage_class>
  template:
    metadata:
      labels:
        redfish-enabled: "true"
        vcp-cluster: <cluster_name>
    spec:
      evictionStrategy: None
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  vcp-cluster: <cluster_name>
              topologyKey: kubernetes.io/hostname
      readinessProbe:
        guestAgentPing: {}
        initialDelaySeconds: 120
        periodSeconds: 20
        timeoutSeconds: 10
        failureThreshold: 3
        successThreshold: 3
      domain:
        rebootPolicy: Terminate
        cpu:
          cores: 8
        memory:
          guest: 16Gi
        devices:
          disks:
            - name: rootdisk
              disk:
                bus: virtio
            - name: cloudinitdisk
              disk:
                bus: virtio
          interfaces:
            - name: default
              macAddress: "52:54:00:00:00:01"
              bridge: {}
      networks:
        - name: default
          multus:
            networkName: <network_attachment_definition>
      volumes:
        - name: rootdisk
          dataVolume:
            name: control-plane-0-disk
        - name: cloudinitdisk
          cloudInitNoCloud:
            userData: |
              #cloud-config
              hostname: control-plane-0
              user: core

    where:

    • <vm_namespace> specifies the namespace for the VMs. Must match the namespace specified in the KubeVirt Redfish chassis configuration.

    • redfish-enabled: "true" is an example label. The label must match the vm_selector labels in the KubeVirt Redfish configuration so the VM is exposed through the Redfish API. You can use any label key and value, as long as both the VM and the KubeVirt Redfish configuration use the same label.

    • vcp-cluster: <cluster_name> identifies which target cluster a VM belongs to. Replace <cluster_name> with the name of your target cluster. This label is used by anti-affinity rules and the pod disruption budget to scope operations to a single target cluster. This is important when a hosting cluster runs VMs for multiple target clusters.

    • evictionStrategy: None prevents the hosting cluster from attempting to live-migrate control plane VMs during node drain operations. Live migration is not supported for virtualized control plane VMs.

    • affinity.podAntiAffinity distributes control plane VMs across different physical nodes so that a single node failure affects only one VM. The label selector uses the vcp-cluster label to scope anti-affinity to VMs belonging to the same target cluster.

    • readinessProbe.guestAgentPing verifies that the QEMU guest agent inside the VM is responsive. The hosting cluster uses this probe to determine whether the VM is healthy before allowing operations that affect other VMs.

    • runStrategy: Halted specifies that VMs must be powered off initially. The installation powers them on by using the Redfish API.

    • rebootPolicy: Terminate specifies the reboot behavior required for Redfish API boot override operations. Ensures the VM terminates cleanly when boot media changes.

      The RebootPolicy feature gate enables the rebootPolicy field in VirtualMachine CR specifications. In OpenShift Virtualization 5.0, this feature gate is enabled by default.

      The rebootPolicy: Terminate configuration is required when deploying a virtualized control plane cluster.

    • cores: 8 and guest: 16Gi specify the minimum recommended resources for control plane nodes.

    • dataVolumeTemplates creates a blank root disk for the VM. The 120Gi value matches the control plane VM storage requirements.

    • <storage_class> specifies the LVM Storage StorageClass on the hosting cluster, for example lvms-vg1.

    • macAddress specifies a fixed MAC address for the VM network interface. Use this same address for the bootMACAddress field in the installation configuration. Assign a unique MAC address to each control plane VM.

    • <network_attachment_definition> specifies the name of a NetworkAttachmentDefinition configured on your hosting cluster. All control plane VMs must share the same L2 network segment. Common options include localnet, Linux bridge, or OVN Layer 2 networks.

  2. Apply the resource by running the following command:

    $ oc apply -f control-plane-0.yaml

    Create further VMs for control-plane-1 and control-plane-2 using the same specification, adjusting the metadata.name, dataVolumeTemplates[].metadata.name, macAddress, and cloud-init hostname for each VM.

  3. Create a PodDisruptionBudget to prevent the hosting cluster from evicting more than one control plane VM at a time:

    apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: vcp-control-plane-pdb
  namespace: <vm_namespace>
spec:
  minAvailable: 2
  selector:
    matchLabels:
      vcp-cluster: <cluster_name>

    where:

    • minAvailable: 2 ensures that at least two control plane VMs remain running during node drain operations, which preserves etcd quorum. You must use minAvailable instead of maxUnavailable because the VirtualMachineInstance controller does not implement the Kubernetes scale subresource. A PDB with maxUnavailable cannot determine the expected pod count for VMs, which causes it to block all evictions.

    • The label selector uses the vcp-cluster label to scope the budget to VMs belonging to the same target cluster.

  4. Apply the resource by running the following command:

    $ oc apply -f vcp-control-plane-pdb.yaml

Manage the hosting cluster for virtualized control planes

Upgrade and perform node maintenance on the hosting cluster that runs virtualized control plane workloads.

Overview of hosting cluster management

A hosting cluster that runs virtualized control plane VMs requires ongoing management to maintain the availability and performance of all target clusters it supports.

Hosting cluster management includes the following tasks:

  • Updating the hosting cluster and OpenShift Virtualization without disrupting the target clusters.

  • Performing node maintenance on hosting cluster nodes while preserving etcd quorum in target clusters.

Because multiple target clusters can share the same hosting cluster, a misconfigured update or unplanned maintenance event on the hosting cluster can affect multiple target clusters simultaneously. Plan and execute all hosting cluster operations with awareness of which target cluster VMs run on which physical nodes.

Update a hosting cluster for virtualized control planes

Update the hosting cluster and OpenShift Virtualization while maintaining the availability of the target clusters.

During a hosting cluster update, the Machine Config Operator drains and reboots nodes one at a time. If pod disruption budgets and anti-affinity rules are configured correctly, the update proceeds without losing etcd quorum in any target cluster.

Prerequisites

  • Control plane VMs are distributed across hosting cluster nodes by using anti-affinity rules.

  • A PodDisruptionBudget with minAvailable: 2 is configured for each target cluster’s control plane VMs.

  • The VM eviction strategy is set to None for all control plane VMs.

Procedure

  1. Verify that all target cluster control plane VMs are healthy before starting the update by running the following command:

    $ oc get vm -A -l <vm_selector_label>=<value>

    Replace <vm_selector_label>=<value> with the label you configured in your KubeVirt Redfish vm_selector, for example redfish-enabled=true.

    All control plane VMs must show a Running status.

  2. Verify etcd health on each target cluster by running the following command:

    $ oc --kubeconfig=<target_cluster_kubeconfig> get etcd -o=jsonpath='{range .items[0].status.conditions[?(@.type=="EtcdMembersAvailable")]}{.message}{end}'

    • target_cluster_kubeconfig is the path to the target cluster’s kubeconfig file.

  3. Start the hosting cluster update by following the standard Red Hat OpenShift Container Platform update process.

    The Machine Config Operator drains and reboots each node in sequence. The PodDisruptionBudget CR prevents more than one control plane VM for each target cluster from being evicted at a time.

  4. Monitor the update progress by running the following commands:

    $ oc get clusterversion
$ oc get nodes

  5. After the hosting cluster update completes, update OpenShift Virtualization if a new version is available.

  6. Verify that all control plane VMs are running after the update by running the following command:

    $ oc get vm -A -l <vm_selector_label>=<value>

    Replace <vm_selector_label>=<value> with the label you configured in your KubeVirt Redfish vm_selector, for example redfish-enabled=true.

    All control plane VMs must show a Running status.

Verification

  1. Verify etcd health on each target cluster after the update by running the following command:

    $ oc --kubeconfig=<target_cluster_kubeconfig> get etcd -o=jsonpath='{range .items[0].status.conditions[?(@.type=="EtcdMembersAvailable")]}{.message}{end}'

    • target_cluster_kubeconfig is the path to the target cluster’s kubeconfig file.

  2. Verify that the target cluster API is responsive by running the following command:

    $ oc --kubeconfig=<target_cluster_kubeconfig> get nodes

    • target_cluster_kubeconfig is the path to the target cluster’s kubeconfig file.

Performing node maintenance on a hosting cluster

Perform maintenance on a hosting cluster node, such as applying operating system updates or hardware repairs, without disrupting the target clusters.

When you drain a hosting cluster node, the control plane VM on that node shuts down. If pod disruption budgets and anti-affinity rules are configured correctly, only one control plane VM for each target cluster is affected, and etcd quorum is preserved.

Prerequisites

  • Control plane VMs are distributed across hosting cluster nodes by using anti-affinity rules.

  • A PodDisruptionBudget with minAvailable: 2 is configured for each target cluster’s control plane VMs.

  • The VM eviction strategy is set to None for all control plane VMs.

Procedure

  1. Identify which control plane VMs are running on the node you plan to maintain by running the following command:

    $ oc get pods --field-selector spec.nodeName=<node_name> -n <vm_namespace> -l vcp-cluster=<cluster_name>

    • <node_name> is the name of the node you plan to maintain.

    • <vm_namespace> is the namespace of the control plane VMs.

    • <cluster_name> is the name of the target cluster.

      Use oc get pods with the spec.nodeName field selector to filter by node. The oc get vmi command does not support the status.nodeName field selector.

  2. Verify that all target clusters affected by this node have healthy etcd quorum before proceeding by running the following command:

    $ oc --kubeconfig=<target_cluster_kubeconfig> get etcd -o=jsonpath='{range .items[0].status.conditions[?(@.type=="EtcdMembersAvailable")]}{.message}{end}'

    • target_cluster_kubeconfig is the path to the target cluster’s kubeconfig file.

  3. Cordon the node to prevent new workloads from being scheduled by running the following command:

    $ oc adm cordon <node_name>

    • <node_name> is the name of the node you plan to maintain.

  4. Drain the node to evict all pods, including control plane VM pods, by running the following command:

    $ oc adm drain <node_name> --ignore-daemonsets --delete-emptydir-data

    • <node_name> is the name of the node you plan to maintain.

      The PodDisruptionBudget ensures that only one control plane VM per target cluster is evicted. The drain operation blocks until the PDB allows eviction.

  5. Verify that the remaining control plane VMs maintain etcd quorum on each affected target cluster by running the following command:

    $ oc --kubeconfig=<target_cluster_kubeconfig> get etcd -o=jsonpath='{range .items[0].status.conditions[?(@.type=="EtcdMembersAvailable")]}{.message}{end}'

    • target_cluster_kubeconfig is the path to the target cluster’s kubeconfig file.

  6. Perform the required maintenance on the physical node.

  7. Uncordon the node to allow workloads to be scheduled again by running the following command:

    $ oc adm uncordon <node_name>

    • <node_name> is the name of the node you plan to maintain.

  8. Verify that the control plane VM restarts on the node and rejoins the target cluster by running the following command:

    $ oc get vmi -A -l <vm_selector_label>=<value>

    Replace <vm_selector_label>=<value> with the label you configured in your KubeVirt Redfish vm_selector, for example redfish-enabled=true.

    All control plane VMs must show a Running phase.

    Use oc get vmi (VirtualMachineInstance) instead of oc get vm (VirtualMachine) to verify the actual runtime state. The VirtualMachine resource reflects the desired state, while the VirtualMachineInstance resource reflects whether the VM is currently running.
Verification

  • Verify etcd health on each affected target cluster by running the following command:

    $ oc --kubeconfig=<target_cluster_kubeconfig> get etcd -o=jsonpath='{range .items[0].status.conditions[?(@.type=="EtcdMembersAvailable")]}{.message}{end}'

    • target_cluster_kubeconfig is the path to the target cluster’s kubeconfig file.
